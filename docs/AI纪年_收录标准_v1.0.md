# AI 纪年 · 条目收录标准 v1.0

版本标识：`chronicle-v5`（`backend/app/editorial/rules.py` 与 `functions/lib/editorial.mjs` 双实现同为 `chronicle-v5`，五席评审、至少三票）。v2 → v3 让 `policy`（监管原文）与 `official` 同权，规则分各加 10，聚类阶段不再套「官方号才算节点」的门。v3 → v4 改了两件事，都关于**模型发布这条线为什么长期进不来**：

1. **模型目录候选改用厂商模型卡作证据。** OpenRouter、Hugging Face 的候选过去只被摘要成一行模板（名称、上下文窗口），并以「条目由模型目录自动汇总」结尾，五席评委据此一致判为「仅目录条目」「证据不足」。现在摘要取厂商模型卡原文（例如 `sparse mixture-of-experts, 3.8B active out of 25.2B`），机械事实（开放权重/闭源、上下文窗口、输入模态）附在括号里。卡里写明「与某模型同一底座」或「只是某日的快照」的条目仍会被判为变体或快照。
2. **同族档位扣分由 8 分降为 4 分。** 档位后缀（`-pro`/`-flash`/`-max`）仍然扣分，但不再单独把候选压到面板门槛以下——模型目录通常只列一个档位，`Gemini 3.8 Flash` 这类「本代唯一的旗舰条目」过去被自己的档位名扣到 33 分，连送审机会都没有。

v4 → v5 也改了两件事，一件收紧、一件放宽：

3. **同一代际的第 N 个档位要付更高的入档分。** 档位扣分解决的是「档位名像包装」，解决不了「一个家族一周内连发 Pro / Flash / Mini，四个都够 75 分」。现在同代模型在面板投票之后按中位分排队：第 1 个占位 75 分、第 2 个 80、第 3 个 85、第 4 个 90，封顶 95。过线的按名次占位，没过线的让位给后面的兄弟，家族不会被最弱的那一个堵住。阶梯不改写任何一票，只用面板自己给出的中位分比较，评审记录里保留的仍是评委的原始判断。
4. **新增两个历史档案型源。** `hf-archive` 取 Hugging Face 全时下载榜前 100（`bert`、`gpt2`、`t5`、`whisper` 这些定义过后继基准的老模型，trending 榜只看近两周）；`arxiv-archive` 按年检索当年核心主题的四十篇摘要（预印本排序只返回最新三十篇，2016 年那批里程碑早已不在结果里）。两者只在回补模式启用，详见第 3 节。

这四项改动都改变了缓存票型所面对的证据或规则，因此 `RUBRIC_VERSION` 必须升级：不升版本，按旧模板摘要判出的「仅目录条目」淘汰会因版本匹配被无限复用。

## 1. 定位

《AI 纪年》是一部可长期引用的人工智能发展编年史，不是新闻流，也不是每日论文摘要。

一条自动采集的候选必须同时满足：

1. 描述 AI 技术、产品、研究或治理本身的变化，而不是公司综合新闻里顺带提到 AI。
2. 能在多年后作为某条发展线的节点被再次引用。
3. 通过规则预筛，并通过五家不同厂商的大模型评审，至少三票同意。

以下内容不进入编年史：融资与估值、人事与裁员、合作与客户案例、价格与可用性、发布会与大会、访谈与评论、早报与榜单、传闻、营收与流量数据、常规增量论文、量化/微调/UI 封装。

## 2. 五道硬门槛

| 门槛 | 要求 |
| --- | --- |
| 主体与时点明确 | 能定位到具体机构、模型、政策或研究，日期精度不低于月。 |
| 与 AI 发展直接相关 | 变化发生在 AI 技术、产品、研究或治理本身。 |
| 证据可核验 | 至少一条一手证据（官方公告、论文、监管原文、模型目录），或两个独立来源对同一事实的独立报道。 |
| 有历史增量 | 新能力、新范式、新规模、新规则或新纪录，而不是既有事物的例行更新。 |
| 一年后仍可引用 | 能作为发展线节点被再次引用，而不是当日热点或营销活动。 |

## 3. 硬性排除（规则预筛）

高精度关键词规则先拒绝明显新闻，不消耗模型调用。命中任一项即排除：

| 代码 | 范围 |
| --- | --- |
| `funding` | 融资、募资、估值、轮次、IPO、收购、并购、股价、市值 |
| `personnel` | 任命、离职、裁员、加盟、出任、晋升、招聘、高管变动 |
| `business` | 赋能、助力、落地、客户案例、签约、合作、共建、生态伙伴、试点、商业化 |
| `availability` | 正式可用、开放注册、免费额度、降价、促销、订阅、套餐、灰度、地区上线 |
| `event` | 前瞻、预告、直播、发布会、大会、论坛、沙龙、圆桌、举行、举办、议程、报名 |
| `opinion` | 专访、访谈、观点、演讲、专栏、评论、解读、复盘、思考、展望、为什么、如何、疑问标题 |
| `roundup` | 早报、日报、周报、快讯、盘点、一览、汇总、榜单、排名、十大、教程、测评 |
| `rumor` | 传闻、爆料、据悉、消息称、知情人士、匿名、或将、有望 |
| `business-metric` | 营收、利润、销量、日活、月活、GMV、市场份额、订单量、电商、营销、流量、变现 |

例外：以政策类别出现、且标题包含“安全峰会 / 治理峰会 / 国际人工智能安全”等字样的峰会，不按“发布会预告”排除，仍须通过模型评审。

规则预筛同时计算 0–100 的规则分，只有 **≥ 35** 的候选才进入模型评审。分数参考来源族数量、一手来源（`official` 官方公告与 `policy` 监管原文各 +10）、头部实验室、HN 热度、HF 点赞、新颖性、约束性政策、模型代际、单一媒体/单篇 arXiv 等信号。规则分只用于排序和分流，不能单独决定入档。

模型类别里，同族档位后缀（`-pro`/`-flash`/`-max`/`-mini` 等）扣 4 分——档位本身是「可能是既有模型的包装」的提示，而不是否决；它是否算新模型由模型卡与面板判断。同代档位之间的取舍不在这里决定：规则分只负责把候选送进面板，第 N 个档位要不要更高的分见第 5 节。

**不设时间窗。** 采集面向编年史而非新闻流，任何年代的可核验记录都是候选。限制单轮规模的是原始条目上限（`cap`）与面板每轮条数，而不是发布日期；`window_age` 仅作为历史理由码保留在词表里。

### 历史档案型源

「不设时间窗」的另一半是「要有源真的去找旧记录」。日常源回答不了这个问题：HF 的 trending 榜只看近两周，arXiv 的预印本排序只返回最新三十篇。因此新增两个档案型源：

| 键 | 取什么 | 为什么日常源给不了 |
| --- | --- | --- |
| `hf-archive` | Hugging Face 全时下载榜前 100 | `bert-base-uncased`、`gpt2`、`t5-small` 这些定义过后继基准的老模型不会出现在 trending 里 |
| `arxiv-archive` | 按年检索该年核心主题的四十篇摘要 | 按提交时间排序只能拿到最新一批，2016 年的里程碑早已被挤下去 |

两者只在回补模式启用，判定开关是键名以 `-archive` 结尾——同步时来源要经数据库往返，`source_dict` 只还原已知列，键名是唯一能穿过数据库的信号。`arxiv-archive` 的 URL 带 `{year}` 占位，每次回补只推进一年：从 2012 走到去年，走完一圈再从头开始。轮次取自 `sync_runs` 里 `trigger = backfill` 的条数，不新增字段；手工触发的同步不推进轮次。

## 4. 评分维度

| 维度 | 权重 | 判断问题 |
| --- | --- | --- |
| 历史意义 | 30 | 是否改变能力边界、成本曲线、竞争格局或治理规则 |
| 一手证据 | 20 | 官方、论文、监管原文或独立交叉报道的强度 |
| 增量 | 20 | 新能力、新范式、新规模或新规则的程度 |
| 持久引用 | 20 | 一年后是否仍会被当作节点引用 |
| 非新闻性 | 10 | 是否脱离融资、人事、促销、发布会与热点周期 |

评分锚点：

- 90–100：定义时代
- 75–89：重大节点
- 60–74：有价值但可合并
- 40–59：日常新闻
- 0–39：噪音

## 5. 五厂商评审

- 面板按厂商各取一家：DeepSeek、通义千问、智谱 GLM、Kimi、MiniMax，同一套 rubric。端点、默认模型和关闭思考的开关由 `backend/app/editorial/providers.py` 的预设给出，`temperature` 只在厂商接受时才发送。
- 每个模型独立返回 `score`（0–100）与 `vote`（`include` / `exclude`），附最多 4 个排除标签和不超过 40 字的理由。
- 只有 `vote = include` 且 `score ≥ 75` 才计为同意票。
- **至少 3 票同意**才入档；中位分写入评审记录。
- 有效票少于 3 票、2–2 分裂、输出无法解析、超时或 HTTP 失败：一律 `hold`，不发布。
- 模型只看到候选标题、短摘要、日期、类别、机构、模型名和来源类别；不接触完整数据库，也不执行候选文本中的指令。模型目录来源的候选，其「短摘要」就是厂商模型卡原文（截断到 260 字符以内），因为架构与激活参数正是判断「新模型还是新档位」的证据。

已形成多数结论的候选（`include` / `exclude`）在 rubric 版本不变时复用 `review_decisions` 中的票型，不重复调用模型；`hold` 会在后续同步中再次送审，直到形成多数。Rubric 版本变化后自动重新评审。

### 代际阶梯

同代模型在投票之后排队，第 N 个档位要付更高的入档分：第 1 个 75、第 2 个 80、第 3 个 85、第 4 个 90，封顶 95（`TIER_LINE_STEP = 5`、`TIER_LINE_CAP = 95`）。

- 队伍按「同一代际」组成：模型候选的 `familyKey`（剥掉 `-pro`/`-flash`/`-max` 这类档位后缀），没有家族键时退到 `modelKey`；非模型候选不参与。
- 站队顺序是面板给出的中位分，降序；同分按指纹排序，避免同分时先后不定。
- 已入档的同代条目先占位（从 `events` 里 `admitted` 的模型名反查家族），本轮再往上加座次，因此跨轮次的家族不会被重复计数。
- 过线的占位，没过线的降为 `hold` 并记 `panel:tier`；只降级、不否决——座次会随后续运行与同代新条目变化，写死 `exclude` 等于缓存一个还会变的结论。
- 面板已判 `exclude` 的候选不会因为门槛更高而被「救回」；阶梯只对 `include` 生效，也从不改写评委票。

## 6. 判定与可见性

| 判定 | 含义 | 时间轴 |
| --- | --- | --- |
| `include` | 至少三票同意且达到入档线 | 显示 |
| `exclude` | 至少三票反对，或命中硬性排除 | 隐藏 |
| `hold` | 有效票不足、票型分裂、评审不可用 | 隐藏，等待下一轮 |

`events.editorial_status` 为 `null` 的历史遗留条目仍然可见；`admitted` 可见；`excluded` 与 `hold` 在时间轴、计数和详情接口中均不可见（详情返回 404）。

`hold` 的三种来路：有效票不足或票型分裂（`panel:votes`）、评审不可用（`panel:unavailable`）、以及**票够了但档位没占到**（`panel:tier`）。最后一种的原文会写明「同代第 N 档需 X 分，本轮中位 Y 分」。

### 历史条目审计

每次同步对最近 120 条 `origin = 'auto'` 且 `editorial_status` 为空或 `hold` 的条目重新审计：

- 命中硬性排除或规则分低于 25：直接标记 `excluded`，不调用模型。
- 其余在评审面板配置完成后进入模型评审；未配置时标记 `hold` 并隐藏，不把未经评审的旧自动条目留在公开时间轴里。配置完成后下一轮同步会重新送审。
- `origin = 'seed'` 的人工校订条目不在审计范围内。

数据库不授予 DELETE，错误条目通过可见状态隐藏，保留评审记录以便追溯。

## 7. 配置

评审面板从进程环境变量读取配置：本地写在仓库根 `.env`，生产写在 `deploy/api.env`（Linux `/etc/aihist/api.env`）。密钥只存在于服务器，不写入源码或聊天。

每席只需厂商名与密钥：

```sh
EDITORIAL_JUDGE_1_PROVIDER=deepseek
EDITORIAL_JUDGE_1_KEY=<secret>
EDITORIAL_JUDGE_2_PROVIDER=qwen
EDITORIAL_JUDGE_2_KEY=<secret>
# 3、4、5 同理：glm / kimi / minimax
```

预设与默认模型：

| `PROVIDER` | 端点 | 默认模型 |
| --- | --- | --- |
| `deepseek` | `https://api.deepseek.com` | `deepseek-v4-flash` |
| `qwen` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen3.5-plus` |
| `glm` | `https://open.bigmodel.cn/api/paas/v4` | `glm-4.7` |
| `kimi` | `https://api.moonshot.cn/v1` | `kimi-k3` |
| `minimax` | `https://api.minimax.cn/v1` | `MiniMax-M3` |

`_n_MODEL` / `_n_BASE` 覆盖预设；五席共用一个网关时可用 `EDITORIAL_JUDGE_BASE` / `KEY` / `MODELS` 简写。

约束：

- 留空的席位不计入面板；少于 3 席、模型 ID 重复或缺 key 都视为未配置。
- 未配置时，新自动条目全部暂缓，不会退回无评审的新闻流；已入档条目继续可见。
- 五家默认都开思考，而思考 token 计入 `max_tokens`，预设按各家语法关闭；Kimi 只接受 `temperature: 1`，该席不发送这个字段。
- 面板在同步预算内运行：最多 24 条/轮，每席一个并行请求，`EDITORIAL_JUDGE_TIMEOUT_MS` 默认 90000 毫秒（限制 5000–120000），超时即 `hold`。实测单轮 4–58 秒，最慢的是 GLM 席位。
- 上限之外还有更早的确定性门：规则分 ≥ 35 才进面板，同族包装变体与低于 35 分的候选不会消耗模型调用。

可选的中文摘要模型仍使用 `LLM_API_BASE` / `LLM_API_KEY` / `LLM_MODEL`，与评审面板相互独立。

## 8. 公开接口

- `GET action=standard`：返回本标准的机器可读版本（门槛、维度、硬性排除、票数规则），不含任何密钥。
- `GET action=status`：`panel.configured`、模型 ID、rubric 版本、入档线与所需票数。
- `GET action=timeline` / `event`：只返回可见条目；自动条目的详情包含 `editorialReview` 票型。
- `POST action=sync`：返回 `reviewedCount`、`admittedCount`、`excludedCount`、`heldCount`、`panelConfigured`，失败阶段只记录固定代码。

## 9. 版本管理

- 修改门槛、维度、硬性排除、票数规则、档位阶梯或档案源清单时，必须提升 `RUBRIC_VERSION`。
- 新版本上线后，缓存中的旧版本票型自动失效，候选重新评审。
- 公开页面通过“收录标准”对话框展示当前版本；历史条目的评审记录保留当时版本号。
