## 2. 任务目标

用户要求：**优化网站 SEO，把站点资源提交到 Google Search Console 和百度站长平台**。

盘点结论（改动前）：站点 SEO 基建已经齐备——`robots.txt`、`sitemap.xml`（173 URL）、172 张静态条目页自带 canonical / OG / Article JSON-LD、首页带 WebSite + Organization JSON-LD；GSC 域名资源已用 DNS 验证。真正缺的是**站长平台接入能力**这一层：

1. 百度站长平台验证需要首页出现 `baidu-site-verification` meta，但首页 `dist/index.html` 是构建产物，手改会被下次构建覆盖，需要一个「有环境变量才注入」的构建期通道；
2. 百度对 XML sitemap 的解析挑剔，主格式是**一行一条的纯文本 URL 清单**，仓库没有这个产物；
3. 百度收录提速要靠**主动推送 API**（`data.zz.baidu.com`），仓库没有推送脚本，且推送 token 是凭证，不能进仓库；
4. 新产物必须纳入既有静态页门禁（`check:pages`）与自检（`check:pages:selftest`），否则「产物漂移」无从发现。

**本次迭代记录环节的边界**：只写迭代记录 + 升产品版本三处 + 跑 `check-version`。不改实现代码、不提交 Git（实现已在 `ab89de9` 上线）。

## 3. 问题诊断

| 现象 | 原因 |
| --- | --- |
| 百度蜘蛛抓不到首页正文，首页无法参与百度侧收录 | 首页 `/` 是纯客户端渲染 SPA：`dist/index.html` 的 `<body>` 只有一个空挂载点，正文全部由 JS 生成，百度蜘蛛不执行 JS。百度侧收录主体只能是 172 张**无 JavaScript 的静态条目页**（`/e/<slug>.html`）——这是已知边界，本轮不改变，只在手册与提交策略上承认它 |
| 只提交 XML sitemap 给百度，收录效果不稳定 | 百度站长平台的 sitemap 读取器对 XML 格式挑剔（历史上有解析失败不报错的先例），官方更推荐纯文本 URL 清单作为「普通收录」的 sitemap 形态 |
| 想让首页带上验证标签，但没有安全入口 | `index.html` 由 Vite 构建产出、再由 `augmentHomepage()` 追加 JSON-LD；若直接把 code 写死进仓库模板，验证标签就与「站点尚未在控制台注册」的状态脱钩，且换域名/换 code 都要发版。需要的是「构建时按环境变量条件注入」：有 code 才写标签，没有则产物与旧版逐字节一致（幂等） |
| GSC 侧要不要也注入 `google-site-verification`？ | GSC 域名资源（Domain property）走 **DNS TXT 验证**，已经生效，不需要任何 meta 标签；所以 `GOOGLE_CODE` 预置但默认留空，只有将来出现需要单独验证的 URL 前缀型资源时才启用 |
| 主动推送的 token 放哪 | token 等同于凭证（可对站点发起推送）。凡是写进仓库的凭证都会在 git 历史里永久可查，因此 `push-baidu.mjs` 的 `BAIDU_PUSH_SITE` / `BAIDU_PUSH_TOKEN` **只从环境变量读**，缺失即报错退出 |
| 新增 `sitemap_baidu.txt` 若不设门禁，日后与 `sitemap.xml` 漂移无人察觉 | 两个清单来自同一份 seed，但一个是 XML 一个是纯文本，任何一侧漏改（比如手工动过 dist）都不会被现有 `check:pages` 发现——检查器此前根本不看这个文件 |

## 4. 方案与实施

### 4.1 核心取舍

1. **单一清单真源**：把 `sitemap.xml` 的 URL 清单抽成公共函数 `sitemapLocs(seeds)`（首页 + 按 `sortDate` 升序的 172 条种子页），`renderSitemap`（XML）与新增的 `renderSitemapTxt`（百度纯文本）都从它渲染。两个格式永远不会漂移，漂移了也过不了 G2。
2. **验证标签走构建注入 + 环境变量，不写死**：`site.config.mjs` 新增 `BAIDU_CODE` / `GOOGLE_CODE`，经 `verifyCode()` 做 `^[\w=+/-]{4,128}$` 格式校验（不合法直接构建失败，防止把截断/带空格的 code 发布出去）；`augmentHomepage()` 仅在 code 存在且产物中尚无 `site-verification` 时注入对应 meta，插在 JSON-LD 块之前，保证控制台爬虫先看到验证标签。
   - **被否决：code 硬编码进 `index.html` 模板**——验证标签的生效条件是「域名已在控制台注册」，这个状态属于部署环境而非代码库；写死等于每次换 code 都发版，且仓库公开（PROVENANCE 允许查看）会把 code 暴露给爬虫模拟器。code 本身是公开 meta 不是秘密，但**发布时机**必须可控。
3. **推送脚本读 `dist/sitemap.xml` 而非 `sitemap_baidu.txt`**：XML 是清单的「正式」产物（`check:pages` 逐条校验过 `<loc>`/`<lastmod>`），txt 只是它的镜像；推送源选前者，镜像坏了也推不出错单。接口每次上限 1 万条，脚本仍按 `--batch`（默认 500）分批 POST，避免一次性长请求在 Windows 终端上失败后无法定位到具体批次。
   - 支持 `--dry-run`（不读 env、不发请求，只列 URL）与 `--limit N`（首次试探配额）；解析 `success` / `left` / `not_same` / `invalid`，错误码表覆盖 4/5/6/7/8/9/14（配额 6、token 失效 7、站点不匹配 8/14 等），任一批次失败即非零退出。
4. **robots.txt 用注释行提示百度纯文本索引**：`# 百度蜘蛛可改用纯文本索引：${SITE_ORIGIN}/sitemap_baidu.txt`——不写成 `Sitemap:` 行，避免 Google 等通用爬虫把一个非标准格式当 sitemap 解析。
5. **门禁同步硬化**：`check:pages` 新增三组断言——`sitemap_baidu.txt` 存在性、每行必须是绝对 http(s) URL、与 `sitemap.xml` 的 `<loc>` 列表**逐条一一对应**；首页验证标签最多 2 条、code 格式合法、且与 `site.config.mjs` 的 `BAIDU_CODE`/`GOOGLE_CODE` 集合完全一致（env 有值而产物无标签、或产物有标签而 env 无值，都算红灯）。为此把 `locs` 从 sitemap 解析块内提到外层作用域。
   - `check-pages-selftest.mjs` 相应新增 2 个反例用例：删掉 `sitemap_baidu.txt` → 期望 `sitemap_baidu.txt is missing`；删掉其中一行 → 期望 `sitemap_baidu.txt: url list differs`。用例总数 21 → **23/23**。
6. **vercel.json 给 `/sitemap_baidu.txt` 加 `Cache-Control: public, max-age=3600`**：与 `/sitemap.xml` 同策略，百度侧每次抓取不必回源全量文件，改清单后 1 小时内自然生效。
7. **文档落一份可照做的操作手册**：`docs/推广/AI纪年SEO_GSC与百度站长_资源提交手册_v1.md`（134 行）——GSC 提交 sitemap 与网址检查步骤；百度站长注册 → 拿验证 code → Vercel 环境变量 `BAIDU_CODE` 注入（含写死进 `index.html` 的备用路径）→ 完成验证 → 提交 `sitemap_baidu.txt` → 主动推送 token 获取与 `npm run push:baidu` 分批命令；收尾清单与 FAQ。README 同步：命令表加 `push:baidu` 行、构建说明段补 `sitemap_baidu.txt` 与验证标签注入说明、脚本清单加 `scripts/push-baidu.mjs`。

### 4.3 关键实现细节

- **注入顺序**：验证 meta 块插在 `data-site-jsonld` 判断之前，注释写明「让控制台爬虫先看到验证标签，即便下方任何东西变化」；重复构建时先测 `/site-verification/` 再注入，保证幂等。
- **无 env 则产物不变**：`BAIDU_CODE` / `GOOGLE_CODE` 均为空时 `verification` 为空串，`augmentHomepage` 不写任何标签——本轮上线时线上就是这条路径（首页无验证标签，属预期），因此 `dist/index.html` 的验证相关变化量为零，仅 `sitemap_baidu.txt`、`robots.txt` 注释行与构建日志有新增。
- **构建日志 `webmaster` 行**：`baidu + google` / `baidu` / `google` / `无（未设 BAIDU_CODE / GOOGLE_CODE）` 四态之一，部署时看日志即可确认标签注入是否生效，不必抓页面。
- **check:pages 的验证标签集合断言**：`expectedVerification` 由 site.config 两个 code 拼出，与产物中实际命中的引擎名（排序后）比对——这条断言让「env 配了但构建没注入」与「产物残留了旧标签」两种事故都在 G2 红灯。
- **push-baidu 的容错层级**：HTTP 层失败（网络/非 JSON 响应）与业务层失败（`error` 码）都只标记该批失败并继续后续批次，最后统一以退出码 1 收尾；这样一次配额中断（error 6）不必人工重跑剩余清单，配合 `--limit`/`--batch` 可断点续推。
- **`--dry-run` 不要求 env**：便于在没有 token 的开发机上验证清单读取与解码（`&amp;` 等实体还原、`^https?://\S+$` 过滤），本地实测能列出全部 173 条。

## 11. 总结

这轮迭代把「站点自己说自己是公开可收录的」变成了「站长平台能确认这一点」：SEO 基建（robots、sitemap、172 张带结构化数据的静态条目页）此前已经齐备，缺的是接入通道本身。现在验证标签有了构建期的条件注入（env 有值才出现、格式不合法即构建失败、门禁比对产物与配置一致），百度要的主格式清单由同一份 URL 真源镜像产出并被 `check:pages` 逐行看住，主动推送有了一个凭证不落库、可 dry-run、可分批、错误码可解释的脚本，操作路径全部写进推广手册可照做执行。产品版本按修订升到 0.15.3，收录规则、种子数据、契约夹具与数据库一层都没动。剩下的三步都在用户手里：百度站长注册拿 code、配环境变量重新部署完成验证、取 token 后跑 `npm run push:baidu`——代码侧已无待办。
