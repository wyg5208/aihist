## 二、任务目标

推广策略把北极星指标定为「外部引用数」，理由是这份档案真正的稀缺性是可核验、可引用。落到 W1 的执行清单上，第一步不是发内容，而是把**管道**接通：

1. 让从平台点进来的陌生人能落到条目页、看到来源、**能订阅**、**能报错**，且后台能计数；
2. 让每个推广渠道的访问在统计里**有名字**，而不是一律落进 `other`；
3. 让公开页面上的自述与真实机制一致——否则"可核验"这一主张从第一屏就站不住。

A1–A5 五项即由此而来。B 站首条内容改为盘点、纠错先走 `mailto` 轻量版，均已确认。

## 三、问题诊断

| 现象 | 原因 |
| --- | --- |
| 页首与页脚写「三个独立模型分别打分；至少两票同意」 | v0.3.1 已把面板扩到五席、门槛提到三票 + 中位分 75，但这两处文案停留在三席时代。卖"可核验"的站点自述错误，被挑出一次就很难挽回 |
| 页脚有「收录标准」「API 申请」，没有订阅 | `growth.py` 具备 `POST /subscribe` 与确认/退订页，但**没有任何页面承载入口**：能力齐全、读者够不着。回访率没有抓手 |
| 读者发现错误后无处提交 | 条目详情与静态页只有"复制永久链接/复制引用"；纠错在规划里写了，实现层没有路由 |
| 小红书、公众号、少数派、即刻的访问全部落 `other` | `SOCIAL_REFERRERS` 未收录这些域名；推广一开跑，最需要看的渠道恰好无法归因 |
| 种子数 148 与 158 并存 | `seed.json` 实际 158 条（含 1912 年前史），README 四处、`.env.example` 一处仍是 148。推广文案会反复引用这个数字 |

## 四、方案与实施

**取舍一：订阅走无 JS 表单页，不做 SPA 对话框。**
与 `/api/v1/open/apply` 同构：后端渲染、内联 CSS、无脚本、`noindex`，在微信内置浏览器与邮件客户端里都能打开，也不需要一次构建。否决了"在 SPA 里加订阅弹窗"——那要动前端状态机，而且静态引用页路径根本用不上。

**取舍二：纠错走 `mailto` 轻量版，不建工单表。**
首月纠错量大概率是每周个位数，而建表 + 迁移 + 管理台队列要占掉半个工作日。现在的做法是一个路由：页面列出该条目的标题、日期、静态页地址与全部来源，出口是一个**预填好条目、日期、链接、三行模板**的 `mailto`；没有邮件客户端的读者可以把同一段模板复制走。风险是依赖读者的邮件客户端，故页面同时提供可选中复制的文本域兜底。升级条件写在这里：**每周纠错超过 5 条**时再换成队列。

**取舍三：限流抽成 `analytics/throttle.py` 的 `SlidingWindow`。**
两个公开表单需要同一条规则（每调用方每小时 5 次），复制一份必然分叉。`apply.py` 的 `allow` / `reset_rate_limit` 保留为薄包装，既有测试与调用点不变。

**取舍四：放行检查器，而不是绕过检查。**
静态页新增 `发现错误？→` 后，`check-pages.mjs` 把 `/api/v1/correct?slug=…` 判为"未知档案地址"并报 158 处红灯。处置是在 `allowedInternalHref` 里**带 slug 校验**地放行——检查的意图是"链接必须指向真实存在的东西"，这里依然成立；把链接改成绝对地址以规避检查才是真的把检查废掉。

**关键实现细节**

- 订阅表单提交后**直接显示确认链接**：这是既有的"无邮件器双确认"模型（`growth.py` 文件头已写明），不是本次的临时做法；页面明说"本站不发确认邮件"，避免读者空等。
- 表单带诱饵字段与来源标记：`?src=bili01` 经 `clean_src` 只保留 `[a-z0-9_-]`、截断 40 字符，落库为 `source_path=/subscribe?src=bili01`；`source_channel` 仍由 referrer 分类得出。
- 纠错页对 `excluded` / `hold` 条目返回 404，与 `/api/v1/events/<slug>` 完全一致，避免出现"JSON 拿不到、HTML 却能看"的旁路。

## 十一、总结

这一版没有加任何新内容，而是把"被引用"这条链上的断点逐段接上：渠道访问有了名字（不再一律 `other`）、读者有了订阅入口（不再只有能力没有门）、发现错误有了出口（静态页与条目详情都能一步到达），并且删掉了公开页面上与真实机制不符的自述。对一个以"可核验"为立身之本的站点来说，最后一项和新增功能同等重要。
