## 2. 任务目标

用户的原始诉求是一句话里的两件事：

> 单独定一条「同代第 N 个档位需要更高分」的规则。新增「历史档案型源」（如 Hugging Face 归档快照、arXiv 按年检索）

两件事指向同一个矛盾的两种解法，因此放在同一轮：

- **收紧**：v0.12.0 把档位扣分从 -8 降到 -4，让本代旗舰能进面板；代价是一个家族一周连发 Pro / Flash / Mini 时，四条都可能够 75 分。档位扣分解决的是「档位名像包装」，解决不了「同一代际到底该留几个位置」。
- **放宽**：时间窗已经放开（`MAX_AGE_DAYS = 0`），但**源本身是留存偏置的**——HF 的 trending 榜只看近两周，arXiv 的预印本排序只给最新三十篇。标准不设时间窗，可没有任何一个源会去问「2016 年发生了什么」。

用户确认的两个口径：

| 项 | 口径 |
| --- | --- |
| 档位加价 | 每档 +5 分，封顶 95（第 1 档 75、第 2 档 80、第 3 档 85、第 4 档 90） |
| 档案源 | 两个源，仅在回补模式启用，每轮回补推进一年 |

## 3. 规则的三个设计判断

### 3.1 阶梯只比较分数，不重写票

一条候选的裁定来自五席各一票，`include` 票 ≥ 3 且中位分 ≥ 75 才算过线。阶梯在这之后运行：

```python
def tier_line(ordinal: int) -> int:
    if ordinal <= 1:
        return INCLUDE_SCORE                       # 75
    return min(TIER_LINE_CAP, INCLUDE_SCORE + TIER_LINE_STEP * (ordinal - 1))
```

- 票型不动。`review_decisions` 里留下的仍是评委当时投的那一票，阶梯只改**结论**（`decision`）与两个记录字段（`tierOrdinal`、`tierLine`）。审计要能回答「是评委不同意，还是座次不够」，改写票会让这两个问题变成一个。
- 用的是面板自己给出的**中位分**，不是规则分。规则分只负责把候选送进面板；「这一代值得留几个位置」应该由读过模型卡的五个评委回答。
- 队伍组成是「同一代际」：`familyKey`（剥 `-pro`/`-flash`/`-max` 这类档位后缀），没有家族键时退到 `modelKey`；只有 `category = "model"` 参与，两条政策不会因为都叫 `eu-ai-act` 就互相挤位置。

### 3.2 被卡住记 `hold`，不是 `exclude`

这是我在这轮里改过一次的想法。最初的版本把「票够了但座次没占到」判成 `exclude`，读起来更干净，但它是错的：

- 座次会变。下一轮回补多了一条同代的高分模型，第 2 档的门槛就从 80 变成 85；反过来，某个已入档的同代条目被运营台上人工改判，座次又会空出来。
- `exclude` 在缓存里是有意义的结论（`rubric_version` 不变就复用票型）。把一个还会动的座次结论写进缓存，等于让下一次运行去复用一条已经不成立的判断。

所以 `hold`。理由码 `panel:tier`，原文写清座次与门槛——`同代第 2 档需 80 分，本轮中位 78 分`。运营台看到的是「暂缓，等下一轮」，不是「评审否决」。同时：**面板已经 `exclude` 的候选不会因为门槛变高被救回来**，阶梯只对 `include` 生效。

### 3.3 已入档的同代条目先占位

`admitted_tiers` 每次运行从 `events` 现算，不维护计数器：

```python
async def _admitted_tiers(session) -> dict[str, int]:
    names = await repo_events.load_admitted_model_names(session)
    ...
```

档案里约 170 条模型行，读一次比维护一个「必须记得在人工改判时同步修正」的计数器便宜。座次因此是「全库已入档的同代条目数 + 本轮排名」，跨轮次不会重复计数。

## 4. 两个档案源

### 4.1 为什么日常源看不见历史

| 源 | 日常返回 | 后果 |
| --- | --- | --- |
| Hugging Face trending | 按近两周热度排序 | `bert`、`gpt2`、`t5`、`whisper` 这些定义过后继基准的老模型永远不会出现 |
| arXiv 预印本列表 | 按 `submittedDate` 倒序、最多三十条 | 2016 年那批里程碑早已被挤出返回窗口 |

这解释了 v0.12.0 的观察：放开时间窗后横扫 2025 年以前，`raw_items` 里 114 条旧记录中几乎全是既有事件的重复命中，模型的旧记录一条也没有——不是标准把它们挡了，是源不记得它们。

### 4.2 两个源

| 键 | URL | 说明 |
| --- | --- | --- |
| `hf-archive` | `https://huggingface.co/api/models?sort=downloads&direction=-1&limit=100` | 全时累计下载榜前 100；`kind=hf`，走现有 HF 解析器 |
| `arxiv-archive` | `...search_query=(ti:transformer+OR+…+OR+ti:agent)+AND+(cat:cs.AI+OR+…)+AND+submittedDate:[{year}01010000+TO+{year}12312359]&sortBy=relevance&max_results=40` | 按年取当年核心主题的 40 篇 |

两个 URL 都实测过：arXiv 返回 `200`（10,604 字节，Atom），HF 返回 `200` / 100 条，前几名是 `sentence-transformers/all-MiniLM-L6-v2`、`google-bert/bert-base-uncased`、`google-t5/t5-small`、`openai-community/gpt2`。也就是说「老经典模型确实在这个榜上」是核实过的事实，不是声明——`verified: True` 是真话。

### 4.3 开关与轮次

- **开关是键名后缀**。`source_dict` 只还原已知列，`historyOnly` 之类的自定义字段在数据库往返回后就不见了；键名是唯一确定能活下来的信号，所以 `is_archive_source()` 判的是 `key.endswith("-archive")`。这个耦合写进了 `catalog.py` 的注释。
- **`{year}` 占位在 pipeline 侧替换**。`resolve_archive_source()` 只替换 URL，不改目录，因此 `sources` 表里存的是带占位符的那一条。
- **轮次取 `sync_runs` 的条数**：`count_runs(session, trigger)` 在 `start_run` **之前**读，所以「本轮」不计入，第一轮回补拿到 2012。手工 `sync` 与每日运行不写 `trigger="backfill"` 的行，因此不推进年份；非历史模式还会把档案源整体过滤掉（一天三成的抓取预算不该花在 2019 上）。
- 年份序列是 `2012 … 去年`，走完一圈回头重来。

## 6. 踩坑与修正

1. **`count_runs` 静默失败。** `repo_sync.py` 原本只导入 `select, update`，`func.count()` 抛 `NameError`，而调用点有一层 `except Exception: history_turn = 0`，于是「每轮推进一年」变成了「永远 2012」。测试 `test_a_backfill_asks_one_year_and_advances` 是唯一发现它的地方——这也说明兜底式 `except` 必须配一条断言边界行为的测试，否则它会把功能缺失伪装成正常。
2. **阶梯测试第一条写错了断言。** 我原以为两个候选里分低的拿第 2 档；实际按分数排 pro(92) → mini(81) → flash(77)，mini 占第 2 档、flash 被要 85 分。错的是断言，不是实现：这恰好验证了「按中位分排队」而不是按到达顺序。
3. **排序键的运算符优先级。** `sorted(..., key=lambda fp: -by_id[fp].get("score"))` 在分数为 `None` 时抛 `TypeError`；改成 `(-(score or 0), fp)`，同分再按指纹定序，避免同分时先后不定。
4. **PowerShell 写 BOM。** `Set-Content -Encoding utf8` 给 `package.json` / `pyproject.toml` 加了 `EF BB BF`，`check-version.mjs` 的 `JSON.parse` 直接抛错。改用 `System.Text.UTF8Encoding($false)` + `WriteAllText` 重写并补行尾换行。

## 10. 下一步

**短期**：

1. 生产 `backfill --max-events 150` 连跑，重点看 `notes` 里出现 `archive:2012`、下一轮 `archive:2013`——这是「轮次真的在走」的唯一外部证据。若第二轮仍是 2012，先查 `sync_runs` 的 `trigger` 值，而不是查年份函数。
2. 盯 `panel:tier` 的条数。它是新规则产生的唯一新结论类型；如果一批家族同时出现多条 `panel:tier`，说明该家族的档位确实在同一周内扎堆，阶梯在做它该做的事。若同一条目跨轮次反复 `panel:tier`，检查 `_admitted_tiers` 的家族键是否把两个不同代际算进了同一队。
3. 看 `hf-archive` 是否带回 `bert`/`gpt2`/`t5` 这类老模型，以及它们是以新节点入档还是并入既有事件——按 v0.12.0 的经验，老发布多半会并入已有的种子节点，这是期望的结果。

**中期**：

1. `arxiv-archive` 的早年份（2012–2016）大概率入档率很低：那几年 cs.AI 的核心主题词表（transformer/alignment/agent）在标题里几乎不出现。年份越早，词表越该换一套（`ti:deep learning`、`ti:recurrent`、`ti:convolutional`），否则前几轮只是在验证「没有结果」。
2. 每轮 40 篇对 2012 年的 cs.AI 是极小的采样。若前几轮确实空白，考虑按 `max_results` 分两页，或把 `sortBy` 换成 `relevance` 以外的组合再取一次。
3. 阶梯目前只按「座次」计数，不区分座次之间的时间间隔。一个家族 2023 年发 Pro、2026 年发 Flash，会被当成第 2 档要 80 分；跨年的档位也许应该重新从 75 起算，这需要先看几轮真实数据再定。

## 11. 总结

这一轮把「同一代该留几个位置」从一件靠面板自由裁量的事，变成一条可复算的规则：面板仍负责判断「这条够不够格」，阶梯负责判断「这一代还有没有位置」。两者用同一份数据（中位分），但回答两个不同的问题，因此阶梯不改写票型——审计里必须能分清「评委否决」与「座次不够」。

收紧的同时也放宽了采集：标准不设时间窗，但源是有记忆的，所以补上两个只问历史问题的源。它们的开关、年份与轮次都落在既有结构上（键名后缀、URL 占位、`sync_runs` 条数），不加字段也不加迁移——档案的边界应该由「这次运行是什么模式」决定，而不是由又一张配置表决定。
