| 项 | 内容 |

## 二、任务目标

两件事，互相依赖：

1. **修掉收录规则的双实现漂移**。生产实现（`backend/app/editorial/rules.py`）早已是 `chronicle-v2` / 五席 / 至少三票，参考实现（`functions/lib/editorial.mjs`）仍停在 `chronicle-v1` / 三席，导致 `npm run check:editorial` 校验的是旧规则，不代表线上行为。
2. **让迭代与发布有一套可执行的规则**。`.qoder/agents/` 下的两份文档是从另一个仓库（WeClaw）整体搬来的，里面的 `release_gate.py`、`update_history/`、`file_version_info.txt`、PySide6 打包链、SSH 推送流程在本仓库全部不存在。文档要按真实链路重写，并落成可跑的脚本，而不是只改措辞。

## 三、问题诊断

### 1. 规则漂移（现象 → 原因）

| 现象 | 原因 |
|---|---|
| `check:editorial` 全绿，但线上是五席评审 | `functions/lib/editorial.mjs` 的 `RUBRIC_VERSION` 停在 `chronicle-v1`、`PANEL_SIZE = 3`，与 `rules.py` 的 `chronicle-v2` / `5` 不一致 |
| 同步记录里出现 `panel:5/3` 这种不可能的比例 | `pipeline.mjs` 把分母硬编码成 `3`（``notes.push(`panel:${okCount}/3`)``），五席全回时就成了 5/3；参照实现 `backend/app/ingest/pipeline.py` 用的是 `len(panel["judges"])` |
| 两票就会写 `review_decisions` | `pipeline.mjs` 的 `outcome.validVotes >= 2`，与 v2 的「至少 3 票才形成结论」不符；Python 侧是 `>= MIN_INCLUDE_VOTES` |
| 面板离线夹具只有三个模型 | `dev/fake-panel.mjs` 的 `PANEL_ENV` 只给了 `judge/alpha,judge/beta,judge/gamma`，五席配置下起不来 |

`check:editorial` 里 9 个用例原本按三席写死了期望值（`2/3 include`、`validVotes === 3`、`panel:3/3`、`standardBody.standard?.minVotes === 2`），所以**只改常量不改断言，结果会是假绿**。

### 2. 机制文档脱节

两份 agent 文档引用的路径、脚本、依赖项在本仓库一个都不存在。按原文档执行会依次失败：找不到 `scripts/release_gate.py`、找不到 `src/__init__.py`、找不到 `update_history/`、`npm install` 里没有 PySide6。更危险的是它假设「版本号只在 `src/__init__.py`」，而本仓库有四个版本族（产品 / `RUBRIC_VERSION` / `SEED_VERSION` / golden 夹具），漏掉任一族都会造成静默不一致。

### 3. 版本号有第四处手写点

`backend/app/main.py` 里 `FastAPI(version="1.0.0")` 与产品版本无关，也不随发布变动，任何「版本一致性」检查都会长期挂着一条无法消除的告警。

### 4. 仓库未纳入版本控制

`git remote -v` 报 `fatal: not a git repository`。没有 `.git` 意味着「发布」只能靠文件拷贝，回滚没有锚点。

## 四、方案与实施

### 4.1 核心取舍

**以 Python 生产实现为语义真源，把 JS 参考实现拉齐**，而不是反向改 Python。理由：五厂商评审（DeepSeek / Qwen / GLM / Kimi / MiniMax）是 `docs/AI纪年_收录标准_v1.0.md` 第 5 节写明的设计，生产侧已在跑；把 Python 退回三席会同时改掉公开文档与线上行为。

**被否决的方案**

- *只改常量，不改 `check-editorial.mjs` 的断言*：三席期望值在五席聚合下会直接报错（实测 9 个用例红），强行改绿等于把检查改成摆设。
- *让 `check-version.mjs` 永久对 `main.py` 报一条 WARN*：门禁里的常驻告警会训练人忽略告警。改为让 `main.py` 从已安装分发包读版本，从根上消除第四处手写点。
- *重导全部 golden*：不必要。规则常量不参与 `assessCandidate` 打分，词表逐条比对无差异，`api-standard.json` / `api-status.json` 里已经是 `chronicle-v2` / `minVotes 3` / `panelSize 5`。重导只会白白改掉 `nowMs`，制造一次假的契约变更。

### 4.3 关键实现细节

- **面板席位分母**：`notes` 字段是排障时唯一能看见「这轮评审到底几席在线」的地方。写死 `3` 会让五席全回显示 `5/3`，运维无法判断是否有席位掉线。改为 `panel.judges.length` 后，三席配置显示 `3/3`，五席配置显示 `5/5`，与 Python 的 f-string 完全一致。
- **写入评审记录的门槛**：`review_decisions` 是决策缓存，命中即不再调用模型。两票就落库会让下一轮同步误判「已形成结论」，把 `hold` 冻结成永久隐藏。改成 `>= MIN_INCLUDE_VOTES` 后，只有真正形成多数的候选才进缓存。
- **`check-version.mjs` 的分级**：产品版本是机械一致性，不一致必然出错，直接红灯；规则版本与种子版本的不一致往往是「有意变更还没配套重导」，红灯会逼人绕过门禁，所以只报 WARN，并要求在迭代记录里逐条说明结论。
- **`release-gate.mjs` 的退出码**：区分「检查不通过」（1）与「环境跑不起来」（2，例如找不到 `backend/.venv`），否则丢依赖会被误读成代码回归。摘要行的 `failed (exit N)` 是子命令退出码，不是门禁自身的退出码。

## 七、发布与回滚

### 7.1 通道 A：静态站（Qoder Sites）

1. 先确认 `SITE_ORIGIN`（当前默认 `https://aihist.net`）。它决定 canonical / `og:url` / `sitemap.xml` / `robots.txt` 的绝对地址，**必须在大构建之前定下来**。
2. `node scripts/release-gate.mjs` 全绿后再构建并发布。`check:pages` 必须与同一次 `npm run build` 配对，否则校验的是上一次产物。
3. 发布回执落到根目录的 `.AI 纪年 · 人工智能发展编年史.qoder.site`（含 `releaseId` / `deploymentId` / `artifactSha256`），该文件已进 `.gitignore`。
4. 回滚 = 用回执里的 `releaseId` 退回上一版静态产物。

**已知风险（本次未修）**：本地 `dist/index.html` 的 canonical 是 `https://aihist.net/`，而托管侧回执里记录的 `indexHtml` canonical 是 `https://ai-chronicle-y92i8y16xjz.qoder.zone/`。两者不一致说明「本地构建时用的 `SITE_ORIGIN`」与「实际托管域名」不是同一个，需在正式对外发布前统一。

### 7.2 通道 B：API 服务器

1. `deploy/windows/install.ps1`（或 Linux 的 `deploy/bootstrap.sh`）：建 venv → `pip install -e backend` → `alembic upgrade head` → 灌种子 → 构建前端。
2. 验证 `GET /api/v1/status`：`seedVersion` 应为 `2026.10.24.6`，`panel.configured` 应为 `true`（五席配置齐全）。
3. 验证 `GET /api/v1/standard`：`version = chronicle-v2`、`panelSize = 5`、`minVotes = 3`、`includeScore = 75`。这是本次改动的线上验收入口。

### 7.3 数据库

本次无迁移、无数据改写，不需要恢复备份。若确需备份，只能用 `deploy/backup.py` 或 `VACUUM INTO`：WAL 模式下直接复制 `.db` 会拿到撕裂的快照。

### 7.4 回滚

| 对象 | 方式 | 注意 |
|---|---|---|
| 静态站 | 用回执 `releaseId` 退回 | 无状态，最安全 |
| 代码 | 回到 v0.1.0 的提交 | 本次是本仓库首次纳入 Git，v0.1.0 没有独立提交，只能按文件回退 |
| 数据库 | 默认**不** `alembic downgrade` | 本次无迁移，无需 downgrade |
| 规则 | 回退 `RUBRIC_VERSION` 会让缓存票型全部失效并触发重评 | 五席改三席属于语义回退，需单独评估，不要顺手改 |

### 7.5 版本控制

本次 `git init` 建立了仓库，首个提交即 v0.2.0。此前的 v0.1.0 状态只存在于文件系统与迭代记录里，没有可回滚的 Git 锚点。

## 十一、总结

这次把「两套实现各跑各的规则」和「规则只写在文档里、没人能跑」这两个问题一起解决了。规则侧，参考实现向生产对齐，`check:editorial` 从校验三席旧规则变成校验五席新规则，面板的票数分母与落库门槛不再依赖手写常量；机制侧，版本一致性从「靠人记住三个文件」变成 `check-version.mjs` 的一个退出码，发布从「照着一份来自别的仓库的清单手工操作」变成 `release-gate.mjs` 的七步串行门禁，并且第一次有了 Git 锚点可以回滚。剩下的最大隐患不在代码里，而是 `SITE_ORIGIN` 与实际托管域名不一致——这会在第一次正式对外发布时暴露成 canonical 错误，已经写进下一步的第一位。
