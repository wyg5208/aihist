## 2. 任务目标

订阅表单从 v0.6.0 起就写着「只在一段时间确实有值得记的条目时发信」，但实际上一封信都不会发出：`subscribers` 只记录同意，`mailer` 只发 API 密钥，管理台说明书还明确写着「本后台不发送邮件，导出 CSV 后在你自己的邮件工具里发」。这句话在页面上挂了四个版本，等于对外承诺了一件没有实现的事。

本次要把这句承诺兑现成一条可运行、可审计、可重试的通道：

1. 每周一发一封，只写这一周新增了什么（日期、一句为什么重要、条目链接），这一周确实没有新增就不发，不发空信。
2. 每封都带收件人自己的退订链接；退订之后不再收到。
3. 每一次投递（成功、失败、失败原因、发出条数、时间）都要留痕，运维能回答「上周一到底发了什么」。
4. 一个地址失败不能连累别人；失败的下一次运行补发；同一个人同一期绝不收到两封。

同时把站点上三处口径不一致的文案统一成「每周一发一封，没有新增就不发」。

## 3. 问题诊断

| 现象 | 原因 |
| --- | --- |
| 订阅了收不到任何邮件 | `mailer` 只有一个入口 `send_api_key`（事务性的密钥通知）。`Subscriber` 的 docstring 直接写着 "delivery is out of scope"，这条通道从未被建起来 |
| 想发也不知道该发给谁、发没发过 | 没有投递账本。`subscribers` 只存 `status`（`pending`/`confirmed`/`unsubscribed`），没有任何「这一期谁收到了」的记录，重跑就一定会重复投递 |
| 40 个地址里第 3 个失败会打断整批 | 原 `_send_sync` 一次一条连接、一条 `with` 语句，异常直接抛出。一个 bounced 地址就能让剩下的 37 个人收不到 |
| 站点文案三个版本各说一套 | 页脚订阅区说「每周一封」，订阅页说「只在一段时间确实有值得记的条目时」，管理台说「本后台不发送邮件」。文案先于功能落地，谁也不知道哪句是真的 |

## 4. 方案与实施

### 4.1 核心取舍

**名单与账本分离。** `subscribers` 回答「谁同意过」，新表 `digest_sends` 回答「实际发了什么」。两者不合并：consent 是状态（会变），delivery 是事实（只增不改写、按 `(issue, email)` 幂等）。`digest_sends` 对 `subscribers` 不建外键，和 `api_key_usage` 一样把地址快照下来——订阅者记录哪天被就地修正，投递行仍能自解释。

**「一期」用 UTC 日期，不用自增期号。** `issue = '2026-11-02'`。手工补发同一天属于同一期（唯一索引挡住重复），下周一是另一期。唯一索引 `(issue, email)` 同时承担三件事：重跑去重、`--force` 原地更新、运行到一半被杀也留得下「谁可能已经收到」。

**空周不发。** 没有新条目不构成一期。一个只有标题的空信比不发更伤订阅关系。这一条写在 `send_weekly` 的第二道门槛上，不是靠调度器判断。

**失败地址下一轮重试，但按时间而不是按期号过滤。** 去重集合取自 `digest_sends` 中 `status='sent'` 且 `at >= since` 的行：昨天失败的地址不在集合里，明天运行会补发；昨天成功的地址在集合里，三天后即便 `issue` 变了也不会被再发一次。

**一次连接走完名单。** `mailer.send_batch` 打开一个 SMTP 会话然后逐封发出，返回每个收件人的 `(ok, error)`。逐条连接等于每条一次 TLS 握手 + 一次登录，大多数服务商会限流。

**退出码只区分一件事。** 空周、没有收件人、没配 SMTP 都是正常的周一，退出 0；只有「有人该收但一封都没发出去」才退 1——那是 SMTP 口令错的样子，连续三个周一看起来都像「安静的周一」是通讯简报悄悄死掉的典型方式。

被否决的方案：

- *直接导出 CSV 人工发*（现状）：没有留痕，无法回答「上周发了谁」，也没有退订闭环。
- *每期邮件用 HTML 模板*：一封纯文本里日期、一句摘要、一条链接已经够用，HTML 反而要维护一套和内联样式赛跑的东西。`SUMMARY_CHARS=160` 的截断逻辑比模板更有用。
- *新增第六个订阅状态或新表存「已发期号」*：都是同一个事实的第二种写法。唯一索引 + 投递行能同时表达。

### 4.3 `send_weekly` 的判断顺序

顺序本身就是「一次跳过的周一要便宜、且不留垃圾行」：

1. `smtp_not_configured` —— 没配 `SMTP_HOST` 就直接返回，一次查询都不发。生产当前就是这一档：订阅功能可用，发信通道待配置，`digest_sends` 不会有半截数据。
2. `no_new_entries` —— 窗口内没有过门槛的新条目，不发空信。
3. 统计整周条数 `total`，列表只取 `MAX_ITEMS=12`。主题与开头写 `total`，正文写「这里只列最新的 12 条，其余 N 条在站点上」：一周 30 条却写「新增 12 条」，是在读者唯一无法核对的地方说谎。
4. `no_recipients` —— 没有 `confirmed` 的地址。
5. `all_delivered` —— 窗口内已经投递成功过的地址被跳过，若全被跳过就到此为止。
6. 写 `queued` 占位 → `send_batch` → 逐行覆盖成 `sent` / `failed`。

第 2 道的「新」是两个窗口的交集，这一点在 `--dry-run` 实测后改了：最初只看 `first_seen_at`，而生产的 159 条事件都是 10/25–10/27 刚灌进档案的，于是首封会写「本周新增 159 条」、正文里排在前面的是 9 月甚至 1912 年的里程碑。读者的提问是「这一周发生了什么」，所以条目自身的 `sort_date` 也必须在窗口内；一个月前发表、今天才入档的文章是好档案、坏新闻。改完生产 `--dry-run` 从 159 条降到 3 条（2026-10-21 之后的真实新闻）。

`--dry-run` 在前五道之后打印一封完整正文但不写库（`reason=dry_run`），用于上线前核对版式；`--force` 跳过第 5 道去重，供人工补发。

新增 14 个用例（`backend/tests/test_digest.py`），全部离线（`mailer.send_batch` 一律 monkeypatch，任何用例都不出网）：

- 空周不发：窗口外的条目不算新增，`digest_sends` 零行。
- **旧闻不算本周新闻**：两天前入档但事件日期在 9 月的条目，`reason=no_new_entries`、不写库（这一例是 `--dry-run` 实测后补的，原因见 §4.3）。

- 窗口内第二次运行：`all_delivered`，不重复发，账本仍是一行。
- 失败地址下一轮补发：两行两条 issue（`failed` 那条是那天的事实），这正是要留的轨迹。

- hold / excluded 条目进不了简报（门槛在 `repo_events.load_new_events` 里，不靠调用方自觉）。
- `--dry-run` 打印正文、不写库。
- 未配置 SMTP：`smtp_not_configured`，不写库。

## 7. 发布与回滚

**静态站（Vercel）**：随 push 自动部署。本次前端只有文案（`MuseumView.tsx`、`Subscribers.tsx`）与 README 变化，无静态产物结构变化。

**API 服务器**（`D:\srv\aihist`，WinSW 服务 `aihist-api`，端口 8001）：

1. `deploy/backup.py` 备份 SQLite（禁止直接复制库文件）。
2. 拉代码，`.venv\python -m pip install -e backend --no-deps`（版本号写进 editable 元数据）。
3. **显式设 `DATABASE_URL`** 后 `alembic upgrade head`：`0005`（若尚未应用）→ `0006_weekly_digest`。
4. 重跑 `deploy/windows/register-tasks.ps1 -DigestAt 07:10` 注册 `aihist-digest`（幂等，`-Force`；其余四个任务的触发时间必须显式传入，不能靠默认值覆盖线上已有的排期）。
5. `Restart-Service aihist-api`。
6. 线上验收：`/api/v1/status` 仍报 `chronicle-v3`；`python -m app.cli weekly-digest --dry-run` 在**未配置 SMTP** 时应打印 `smtp_not_configured` 并退 0；`Get-ScheduledTask aihist-digest` 存在且为 Ready。

**发信前置条件（手工）**：生产目前没有 `SMTP_HOST`，所以本版上线后不会有任何邮件发出，这是预期行为。真正开始发信前需要在服务 XML 的 `<env>` 里补 SMTP 六项，然后用 `--dry-run` 看一封完整正文，再手工跑一次 `weekly-digest` 确认第一封到达。

**回滚**：`alembic downgrade 0005` 删除 `digest_sends`（会丢掉投递记录）；只停发信则停用/删除 `aihist-digest` 计划任务，代码留着不影响任何既有通道。

## 11. 总结

上一版把「采什么、为什么没采」变成了可查的账本；这一版把同一套纪律用在唯一一件往外发的事情上：发什么由查询决定（窗口 + 门槛 + 上限），发给谁由 consent 决定（只认 `confirmed`），发没发过由账本决定（`(issue, email)` 唯一 + 先占位后覆盖），发失败不连累别人（逐条结果、逐行提交、永不抛）。站点上那句挂了四个版本的「每周一封」从这一版起有代码支撑，而不是一句文案。代价很小——一张表、一个子命令、一个计划任务；风险也很小，因为发信通道默认关闭，未配置 SMTP 时它安静地退 0。
