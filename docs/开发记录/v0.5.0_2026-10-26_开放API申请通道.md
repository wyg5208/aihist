**为什么是功能而不是重大。** 判断依据只有两条：既有能力有没有被删、既有契约有没有被改。本轮两条都不成立——`/api/v1/open/events` 的认证、配额、字段一字未动，`api_keys` 表与手工签发通道保持原样，`RUBRIC_VERSION` / `SEED_VERSION` / golden 全部未变，新增迁移是纯加法（一张新表 + 两个索引）。新表、新页面、新接口都在「新增能力、向后兼容」这一档，判 `Y+1`。

**为什么不是账号体系。** 路线 A（审核制签发）与路线 B（注册登录 + 自助签发）是两条不同的产品路线，不是同一件事的两档实现。本轮选 A 的理由写在下面「三、问题诊断」第 1 条与「四、方案与实施」的被否决方案里：账号体系是一个单人维护者要永久承担的负债（找回密码、会话安全、注销与数据删除、异常登录处置），而现阶段能验证需求的信号（有多少人真的来申请、申请里写了什么用途、拿到密钥后有没有调用）在 A 路线里全都能拿到。等出现「同一批人反复申请」或「申请量超过人工处理能力」的证据，再谈 B。

## 二、任务目标

1. **回答上线条件问题**：用户问「现在系统对外提供的 API 服务，上线条件具备了吗」——需要逐项核对数据面、凭证面、运维面的真实状态，而不是给一个笼统的「可以/不可以」。
2. **补上缺口里最轻的一环**：现有系统能签发密钥、能算配额、能审计，但没有任何对外的申请入口，也没有把密钥送到申请者手上的通道。这两件事是「API 能不能真的对外」的最小闭环。
3. **不做账号体系**：用「表单提交 → 人工审核 → 批准即签发」替代注册登录，避免为尚未验证的需求先建一套身份系统。
4. **确定 API 内容与价值**：把「提供什么」写进申请页与批准邮件（条目与公开时间轴一致、每条带来源、按月配额、只读），让用户在提交前就知道自己能得到什么。

## 三、问题诊断

### 1. 数据面与凭证面已经齐了，唯独缺「入口」与「送达」

| 现象 | 原因 |
|---|---|
| `/api/v1/open/events` 与 `/open/events/{slug}` 已可用，但没人能拿到密钥 | 签发只有管理台 `#/keys` 一条路，只服务于运营自己知道的对象；站点上没有任何入口指向「如何申请」 |
| 密钥明文只在创建响应里出现一次，靠人工复制粘贴转达 | 没有邮件能力（`growth.py` 明确写过「本后台不发信」），运营要自己开邮箱手动发 |
| 申请意向无处落地 | 没有申请表、没有落库的表、没有「待办队列」；有意向只能通过站外渠道（邮件、私信）零散到达，事后无法回答「谁在什么时候申请过」 |

### 2. 直接把注册登录端上来，成本远大于当前收益

| 现象 | 原因 |
|---|---|
| 账号体系要背一整套生命周期 | 注册、邮箱验证、登录、找回密码、会话失效、注销与数据删除、异常登录处置，每一项都要有对应页面、接口、测试与运维预案 |
| 现有系统里没有任何身份表 | 只有 `admin_users`（运营账号），把申请人塞进同一张表会把「付费/合作方」与「内部操作者」两种权限主语混在一起，权限模型要重写 |
| 需求尚未验证 | 开放 API 在自家产品规划里属于第二阶段（2026-12-31 复盘后），此时先建账号体系等于为假设中的规模付固定成本 |

### 3. 公开表单是唯一一处「陌生人可控文本」进入系统的路径

| 现象 | 原因 |
|---|---|
| 一旦有公开 POST，就会有人拿它当免费的写入端点 | 没有限流、没有去重时，一次脚本就能把队列刷成几千条，人工审核直接失效 |
| 「用途」是自由文本，会被渲染进管理台 | 若前端用 `dangerouslySetInnerHTML` 之类的写法，就是存储型 XSS；这条路径必须按不可信输入处理 |
| 站点 URL 也可能是 `javascript:` | 管理台会把它渲染成可点击链接，`javascript:` 协议直接是 XSS 载荷 |

### 4. 邮件是不可靠依赖，不能让它决定签发成败

| 现象 | 原因 |
|---|---|
| SMTP 服务器可能没配、可能挂了、可能把信扔进垃圾箱 | 密钥在批准的那一刻已经写进库；若发信失败要回滚审批，等于让邮件服务决定业务 |
| 明文只有一次 | 一旦邮件丢失且明文没留下，申请者只能重新申请；运营需要一条「手动转发」的兜底路径 |
| 把失败当异常抛出去会污染审计 | 审批已提交、审计已写入，再抛 500 会让运营以为没批准，重复操作又撞 409 |

## 四、方案与实施

### 核心取舍

| 决定 | 理由 |
|---|---|
| 申请页由**后端渲染 HTML**，不是 SPA 页面 | 一个没有 JS 依赖的表单不需要构建、不需要路由、不需要 `vercel.json` 改动；`growth.py` 的退订页已经确立了这个模式（内联 CSS、`noindex`、无脚本） |
| 表单路径放在 `/api/v1/open/apply` | `Caddyfile.api` 只放行 `/api` 与 `/go` 两个前缀，放在 `/api` 下不需要改反代；Vercel 的 `/api/*` 回源规则已覆盖，浏览器始终只看 `aihist.net` |
| 提交只写 `pending` 行，**没有自动签发端点** | 审核是「这把密钥值不值」的判断点；存在可脚本化的自动签发路径，等于把这层判断取消 |
| 批准时在同一事务里建 key 与关申请 | 崩在中间会留下孤儿凭证或「已批准但无密钥」的行，两种都解释不清 |
| 邮件在 commit 之后发，且**永不抛异常** | 密钥已存在，发信结果是一份报告（`sent` / `error`），不是能否批准的前提 |
| 请求体手动 `parse_qs`，不引入 `python-multipart` | 表单只发 `application/x-www-form-urlencoded`；为一个字段集装一个只为 multipart 存在的依赖不值得 |
| 拒绝保留行 | 「三月时这个地址申请过、我们说过什么」必须可查；删行会让下一次申请看起来像第一次 |
| 双重去重：同邮箱只允许一条 `pending` | 已批准/已拒绝的地址再次申请是人的判断（丢了密钥、第二个产品），不能静默拦掉 |
| 诱饵字段命中时**返回与成功页完全一致的页面** | 告诉机器人哪里露馅，等于教它下次绕过；不落库即可 |

### 关键实现细节

- **限流键是 IP 摘要，不是明文 IP**：`ip_digest(ip, settings)`，与审计日志同一套盐；进程内 `_hits` 滑动窗口，与 `track.py` 同样的取舍（假定单 worker，缓存而非状态）。
- **纯文本邮件里给的是可直接粘贴的命令**：`curl -H "X-API-Key: …" …/api/v1/open/events`。HTML 邮件里的密钥等于一张截图里的密钥。
- **批准响应的形状**：`{ok, application, key, plaintext, email: {configured, sent, error}}`。管理台据此分三种提示：未配置（手动转发）、已发（成功）、发了但失败（手动转发 + 红色提示）。
- **表单页的三个响应头**：`cache-control: no-store`、`x-robots-tag: noindex, nofollow`、`referrer-policy: no-referrer`。申请页不该被搜索到，也不该把地址泄给第三方。
- **`pending` 去重按规范化邮箱**：`repo_growth.normalize_email` 复用订阅名单那一套，`A@B` 与 `a@b` 不会变成两条。

### 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 注册登录 + 自助签发（路线 B） | 见「三、问题诊断」第 2 条；在需求未验证时先承担完整身份系统 |
| 申请页做成 SPA 页面（`/apply` 新路由） | 需要改 `vercel.json`、`check-pages` 与构建产物，只为一张四字段表单；且无 JS 环境下不可用 |
| 用 `python-multipart` + FastAPI 的 `Form(...)` | 为一个 URL-encoded 表单引入新依赖；手动 `parse_qs` 十几行就够（代价：不支持 multipart，若将来要传附件再补） |
| 提交后自动签发密钥 | 审核是产品判断点；自动签发等于把配额与滥用风险交给陌生人 |
| 拒绝时删除行 | 与「审计要能回答三个月前发生了什么」直接冲突 |
| 引入确认令牌（先确认邮箱再进队列） | 批准邮件本身已经是「控制该地址」的证明，再存一个令牌只是多一个要过期的秘密，不改变信任模型 |
| 建 outbox 表 + 重试队列 | 一封信、人工兜底一次点击就够；重试队列在没有量的时候只是多一张要维护的表 |
| 把配额做成申请者自填 | 配额是成本决策，由审核人按用途给出，默认 1000 |

## 七、发布与回滚

- **静态站（Vercel / Qoder Sites）**：重新构建发布 `dist/` 即可生效；本轮只改 SPA 页脚与管理台 bundle，`/e/*.html` 与 sitemap 未变，无需重新校验引用页数量，但仍按惯例用同一次构建跑 `check:pages`。
- **API 服务器（Windows / Linux）**：
  1. `deploy/backup.py`（SQLite 备份 API）先备份 `aihist.db`，不要直接复制文件（WAL 下会得到撕裂快照）；
  2. 更新代码后 `alembic upgrade head`（新增 `0003_open_applications`，纯建表）；
  3. `pip install -e backend` 刷新分发元数据，`/api/v1/docs` 的版本号随之变成 0.5.0；
  4. 需要自动发信时在 `api.env` 填 `SMTP_*` 并重启服务；不填则审批后由运营复制明文手动转发；
  5. `OPEN_API_ENABLED` 保持 `false` 时，申请页与读接口一起 404——**先切开关再对外宣传**，开关本身是上线动作，不是部署细节。
- **回滚**：`alembic downgrade 0002_admin_console` 删除新表与索引（申请记录随之丢失，回滚前先导出）；代码回退到 v0.4.0 后新路由消失，前端页脚链接会 404，属可接受降级。静态站用托管回执里的 `releaseId` 退回上一版。

## 九、下一步

**短期（本轮之后的运维动作）**

1. 线上把 `OPEN_API_ENABLED=true` 之前，先完成 v0.4.0 遗留的四项线上验收（Vercel 的 POST 转发、`api.aihist.net/health`、DNS 切换、真机 DryRun）——申请表单是 POST，回源转发没验证过就等于没上线。
2. 需要自动发信时配 `SMTP_*`，用一个真实邮箱走一遍「提交 → 批准 → 收信 → 用密钥 curl」的闭环；不配也能用，只是运营多一步复制。
3. 服务器执行 `alembic upgrade head` + `pip install -e backend`，把运行时版本对齐 0.5.0。

**中期（有数据之后）**

1. 观察三件事：申请量、用途描述的分布、签发后 30 天的调用量。三者决定了「API 内容分层」下一步该补哪一层（L1 增量拉取已具备，L2 分类/时间窗过滤与 L3 批量导出尚未做）。
2. 若出现「同一批地址反复申请」或「申请量超过人工处理能力」，再评估路线 B（账号体系）；判断依据不是感觉，是队列长度与处理时延。
3. 若密钥开始被真实产品嵌入，加一条「配额用量接近上限」的管理台提醒，避免调用方无预告地撞 429。

## 十一、总结

这轮把「API 能不能真的对外」从一句话变成了一条可执行的通道：陌生人在站点页脚点一下就能提交申请，运营在管理台读完用途后批准，密钥当场签发并（可选地）直接寄到对方邮箱，全程留审计。比之前强的地方不在功能多少，而在于三件事第一次同时成立——**入口是公开的、签发是人工判断的、送达不依赖运气**：没有账号体系的那套长期负债，也没有把「邮件能不能发出去」变成「密钥能不能发出去」。剩下的不确定性（会不会真的有人申请、申请来做什么）现在可以靠在真实队列里看，而不必靠讨论。
