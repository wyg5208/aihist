## 2. 任务目标

来自一条线上提问：「如何加速图片的渲染，避免加载过慢的问题。还有服务器并发性能瓶颈有没有好的方案。」

两个方向都要基于仓库里的真实配置给结论，不接受「加缓存、加机器」这种没有数据支撑的回答。所以先做测量，再改。

## 3. 问题诊断

### 3.1 图片

| 现象 | 原因 |
| --- | --- |
| 每一屏首次出图要等 300–600ms；重看同一屏仍然不快 | `/visuals/*` 在 `vercel.json` 里没有任何 `Cache-Control` 规则（只有 `/assets`、`/e`、`/sitemap.xml`），Vite 拷贝 `public/` 时文件名不带哈希，平台回落到 `public, max-age=0, must-revalidate`——浏览器每次都要回源校验。实测首次 `x-vercel-cache: MISS`、TTFB 303–582ms，二次仍 219–280ms |
| 换屏瞬间有一块空白 | `ShowOverlay` 只预取下一屏的摘要 JSON（`prefetchEvent`），**图片零预取**；8 秒一屏的节奏下，图片是切到那一屏才开始下载 |
| 单张偏重 | 900×1125 JPEG(q88) 共 3612KB，单张 92–321KB；桌面画框实测约 676×780（`.show-slide` 是 0.94fr/1.06fr），900w 是 1.33 倍过采样，且全程未用 WebP/AVIF |
| `<img>` 无渲染提示 | 只有 `src/alt/style/onError`，没有 `decoding`、`sizes`、`srcset`、`fetchpriority` |

### 3.2 接口

| 现象 | 原因 |
| --- | --- |
| 20 路并发时 `/api/v1/timeline` 的 p50 从 145ms 掉到 1406ms，30 路 p95 到 2.6s | 单请求 145ms 里主要是 168 条 ORM→dict 与 gzip 的 CPU；线上后端是单进程，约 7–10 rps 就饱和 |
| 每个访客首屏都实打实打一次源站 | 全链路没有一层缓存：`vercel.json` 对 `/api/*` 明确写 `CDN-Cache-Control: no-store` 与 `x-vercel-enable-rewrite-caching: 0`（把边缘 CDN 完全旁路），源站 nginx 没有 `proxy_cache`，`src/api.ts` 还硬写 `cache: "no-store"` |
| 每次页面加载白取一张图和一条详情 | `ShowOverlay` 的 `<dialog>` 关闭时仍走「非 setup 就渲染整屏」的分支，`ShowSlide` 挂在 `queue[0]` 上，`useEventDetail(..., true)` 随即发起 `GET /api/v1/events?id=`。CDP 里能看到 644ms 时请求第一屏配图 |

### 3.3 一个必须先纠正的前提

`deploy/aihist-api.service` 里的 `--workers 2` 是 Linux 通道的历史文件，不在线上。线上是 Windows：WinSW 服务 `aihist-api` → `D:\srv\aihist\.venv` → `uvicorn --port 8001`，**没有 `--workers`，即单进程**；`deploy/windows/install-service.ps1` 有注释说明这是刻意的——`--workers N`（哪怕 N=1）会启动多进程监督器，每个 worker 各有一套进程内 track 限流窗口、各一个 SQLite 写池，并且 WinSW 抓不到子进程日志。

## 4. 方案与实施

### 4.1 图片：两档 WebP + 预取 + 长效缓存

| 决定 | 理由 |
| --- | --- |
| 预生成 760w(`q80`) 与 900w(`q78`) 两档 WebP，保留 JPEG 作 `<img src>` 回退 | 本机 `ffmpeg` 已带 `libwebp`，不引入 `sharp` 等新依赖；两档覆盖 DPR1 桌面（676→760w）、DPR2 桌面与 DPR3 手机（→900w），再高的档位在这个画框里看不出来 |
| `<picture>` + `source type="image/webp"` + `srcSet="…-760.webp 760w, ….webp 900w"` | 浏览器按 `sizes` 与 DPR 自己挑，不用 JS 判断 |
| `sizes="(max-width: 900px) 100vw, 47vw"` 与预取共用一处常量 `SHOW_IMAGE_SIZES` | 断点与 `0.94fr/1.06fr` 的 47% 只写一遍，改版式时不会两边打架 |
| WebP 失败先退 JPEG、JPEG 失败再退图版 | `onError` 分两级：`webpFailed` 只影响 WebP 那一档，避免一个 404 把整屏降级成图版 |
| 预取「当前 + 后两屏」，按视口×DPR 只取一档 | 取两档等于把体积翻倍；按需挑一档，猜窄了浏览器还会自己回退 |
| `/visuals/:path*` 给 30 天 + `stale-while-revalidate=7d` | 文件名不带哈希，用 `immutable` 会让换图长期不生效；30 天足够吃掉重复放映，换图时改文件名或加 `?v=` 即可 |
| `phase === "closed"` 时不渲染整屏 | 关闭态的对话框不该挂 `ShowSlide`，这是每次访问都在付费的浪费 |

被否决的：AVIF（`libaom-av1` 可用，还能再省约 20%，但要三层 `<picture>`、编码也慢，收益递减）；只放大 `max-age` 不上 WebP（解决重复访问，不解决首次）；给 `<img>` 加 `width/height`（画框尺寸由 grid 决定，本来就没有 CLS，加了只是噪声）。

### 4.2 接口：只让三个无副作用的公开读可缓存

| 决定 | 理由 |
| --- | --- |
| 只放行 `/api/v1/timeline`、`/status`、`/standard` | 三个都是无副作用读，数据一天只变一次；`admin`、`track`、`events`、`apply`、`correct`、`go` 一律保持 `no-store` |
| 源站 nginx `proxy_cache`（60s，`standard` 1h）+ 边缘 `s-maxage=60` 双层 | 源站缓存管住直连与 Vercel 回源，边缘缓存再吃掉重复回源；两层 TTL 一致，不会互相喂旧数据 |
| `proxy_cache_lock on` + `use_stale updating` + `background_update on` | 并发首击只回源一次；上游抖动时先给旧值，不让读者看 502 |
| 三个 location 里重写 `X-Content-Type-Options` / `Referrer-Policy` | nginx 的 `add_header` 在子块里会替换掉继承值，不重写就等于把安全头丢了（这是 `aihist-api.conf` 里已经踩过的坑） |
| `src/api.ts` 默认仍是 `no-store`，只有这三个接口传 `cache: "default"` | 管理台的读必须新鲜；`requestJson` 里 `...init` 在 `cache` 之后，改动只是给调用方一个显式入口 |
| 不加 worker | 缓存后源站单发 18ms、30 并发 p95 97ms，拐点已经不由 worker 数决定；加 worker 反而破坏 track 限流窗口与 WinSW 日志这两条现有约定 |

## 9. 下一步

## 11. 总结

图片从「每次都要回源校验 + 切屏才开始下载」变成「30 天缓存 + 开播即预取后两屏」，单屏传输从 298KB 降到 130KB；接口从「每个访客都实打实打一次源站、20 并发就排队」变成「源站单发 18ms、30 并发 p95 97ms」。这两件事都不需要加机器：之前缺的是缓存策略、预取和一层源站缓存，而不是算力。
