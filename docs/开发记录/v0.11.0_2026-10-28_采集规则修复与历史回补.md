## 2. 任务目标

用户在生产「采集库」里看到两个排除理由占了绝大多数，判定口径值得商榷：

> 我看到采集库中有大量 模型条目不合适，超出时间窗 这两个原因被排除的，这个值得商榷。请仔细排查下，大模型条目不合适的原因和规则要检查下，我看到比如 DeepSeek-v4.1-Flash-1017 这种大模型有突破性表现的也可以纳入。时间窗的话我认为可以放开，因为需要补充过往几年中的所有可用记录。

拆成两条可验收的目标：

**A. `model_filter`（界面标签「模型条目不适用」）要能放过第一方发布。** 判据必须回答「这个仓库是不是别人家的模型被重新打包」，而不是「名字里有没有 fp8 / gguf」。

**B. 时间窗放开，并且真的能把过往年份补进来。** 放开窗口只是第一步；如果每源只取 40 条、去重只看近两年，旧条目依然永远进不来，所以必须同时给一条回补通道。

执行中确认的四项决策：死源逐个改写入口、由后台点探活启用（前一轮已完成）；回补**每轮 150 条、多跑几轮**、裁定**走评审面板正常流程**。

### 3.2 `window_age`：窗口不是「编年史」需要的东西

### 3.3 放开窗口本身不够：三处隐藏耦合

| 耦合 | 位置 | 只放开窗口会发生什么 |
| --- | --- | --- |
| 每源 40 条 | `interleave_candidates` 的 `rows[:per_source]` | 目录型源永远只交出最新 40 条，第 41 条（往往是更早的发布）永远拿不到名额 |
| 原始条目上限 320 | `settings.collect_raw_cap` | 1018 条候选按轮转排序后只留 320 条，其余标 `cap_raw` |
| 去重只看近两年、只取最新 600 行 | `run_sync` → `load_recent_events(now.year - 2, 600)` | 2023 年的条目在库里看不见，被当成新条目再插一次；而 `load_recent_events` 返回的是**最新** 600 行，回补越往后，最该被认出来的旧条目越先被挤出窗口 |

### 3.4 面板一次只吃得下 24 条

`MAX_COMPLETION_TOKENS = 2400` 是照着「一次投票 24 条」定下的，而五席面板把**整批候选塞进一个请求**。若把 `panel_batch` 提到 150，回复会在第 24 条附近被截断，`parse_judge_content` 拿到半个 JSON，整批记为 `invalid_json` → 全部 `held`。也就是说「每轮 150 条」在旧面板下等于「每轮 0 条入库」。

## 4. 方案与实施

### 4.1 核心取舍

1. **时间窗保留能力、默认关闭**：`MAX_AGE_DAYS = 0` + `too_old(days <= 0)` 恒为假。窗口变成可调的策略参数，而不是每个解析器的硬编码。日期缺失仍然是硬门槛（`date_missing`）——没有日期就无法在编年史上定位。
2. **衍生判据换成「作者」**：`is_derived_repo(model_id, tags)` 只在两种情况下判真——`base_model:` 的上游作者与仓库作者不同，或上游是自己且仓库名带量化/打包后缀（`…-GGUF`、`…-4GB`、`…-comfy`）。没有 `base_model:` 标签的第一方发布一律放行。
3. **回补走同一条流水线，四个旋钮调大**：`backfill` 不加第二套逻辑，只把 `per_source=None`（不切每源 40）、`raw_cap=1500`、`new_event_cap = panel_batch = 150`、`history_min_year=1900` 传进 `run_sync`。日常定时任务一个参数都没动。
4. **面板按 `BALLOT_SIZE` 分批投票再合并**：把「一批一次请求」改成「一片一次请求」，每片 24 条。某一片失败只损失该片的票，其余片照常计票——这在原来也不可能更差（原来整批共命运）。
5. **双实现同步**：`functions/lib/normalize.mjs` 与 Python 逐行对齐后重新导出 golden（1018 candidates），parity 测试继续逐字段比对。

被否决的做法（与理由）：给 `panel_batch` 直接设成 24（那样每轮只有 24 条能裁决，用户确认的是 150，且「顺延」的条目会被下一轮同样的排序再次挤掉）；把 `MAX_COMPLETION_TOKENS` 提到 6000（单条投票的稳定性会随长度下降，且各厂商上限不一致）；给回补单独写一个 `cluster` 或跳过面板（用户在两项选择里都明确要「走评审面板正常裁定」）；把窗口改成一个全局 `settings` 值（解析器语义不同，且本次目标就是「不要窗口」）；保留 tags 关键词判据再加白名单（每来一个新厂商就要改一次代码）。

### 4.3 实现中查出来的两个缺陷

1. **`BACKFILL_RAW_CAP = 800` 是错的**。回补时 `per_source=None` 会让 17 个源的候选全部进入轮转，1018 条里最老的 218 条被 `cap_raw` 切掉；而每次回补看到的都是同一批 1018 条、同样的顺序，这 218 条**永远**轮不到。改成 1500（覆盖当前候选量并留余量），新增条目上限仍由 `new_event_cap` 控制，不会一次灌满。
2. **去重窗口对整个档案取「最新 N 行」**。`load_recent_events` 是 `order_by(sort_date.desc()).limit(n)`，回补把 `min_year` 放宽到 1900 之后，600 行的上限恰好优先保留最新条目、把 2023 年的挤出去——正是要回补的那批。实测 5,000 行 × 1,018 候选在 `cluster_candidates` 里 24.4 s（600 行 6.1 s、2,000 行 10.7 s），落在 30 分钟预算内，所以回补固定用 `HISTORY_EVENT_LIMIT = 5000`。

### 4.4 回补的运行方式

```
backend\.venv\Scripts\python.exe -m app.cli backfill --dry-run --max-events 150   # 只看不写
backend\.venv\Scripts\python.exe -m app.cli backfill --max-events 150             # 真正落库
```

每轮的推进保证：已经入档的条目在去重阶段被认出来（不占 `new_event_cap`），所以第二轮会把「下一批 150 条」变成新事件，而不是反复处理同 150 条。`--dry-run` 只做抓取与 normalize，打印候选总数、按源分布与最老 5 条，适合在正式回补前确认口径。

3. `hf-textgen` / `hf-trending` 的 `below_likes`（点赞 < 20）会在回补后成为新的主要丢弃理由，届时再判断阈值是否要按「历史条目」另设一档。

**中期**：

1. `interleave_candidates` 的每源 40 条对目录型源始终是个截断点：可以考虑按「相对上次采集的新增位置」轮转，而不是固定取最新 40 条。
2. 去重成本（5,000 行 × 1,000 候选 = 24 s）随档案增长会变慢，值得给 `cluster_candidates` 加按年份/类别的桶索引，而不是靠 limit 控制。
3. `backfill` 与定时任务共用租约：长回补会挡住当天的定时采集，建议在后台「采集库」显示「回补进行中」以免运维误判为卡死。

## 11. 总结

这两条排除理由都不是「标准太严」，而是**实现选错了判据**：`model_filter` 用「有没有量化 tag」代替了「是谁发布的」，`window_age` 把新闻源的保鲜期当成了编年史的收录边界。前者让 DeepSeek 全系发布被判为「模型条目不适用」，后者让上一轮新启用的 `qwen-blog` 与 `nist` 一条都没进来。

修法保持最小的语义变化：日期仍是硬门槛，`base_model:` 才是衍生的判据；窗口能力留着但默认关闭。真正的增量是承认「放开窗口」不只是一行常量——每源 40 条、原始上限、去重窗口和面板票数上限，四个地方都在暗中决定历史条目能不能进来；少动一个，回补就是空跑。
