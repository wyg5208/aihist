## 2. 任务目标

两个诉求，各自对应一条可验证的验收线：

**A. 信源是否足够、能否扩展。** 现有 17 条源是 `backend/app/ingest/sources.py` 的模块常量，`ALLOWED_HOSTS` 是 15 个域名的 `frozenset`，加一个 RSS 源要改代码、重新发布，而且新 host 不在白名单会被 `bad_redirect` 判死。目标：信源变成一张表，后台可新增/编辑/启停/探活任意 RSS、Atom、sitemap 源；按已确认的四类优先级（官方实验室与厂商、中文媒体、学术研究、政策法规）补齐候选；每个候选必须探活通过才允许启用。

**B. 采集库。** 现状是 `raw_items` 只写不可读——没有 API、没有页面、没有裁决字段，被 normalize 丢弃、被 180 条上限截断的条目完全不可见。目标：每条抓到的条目（含丢弃的）在库里留一行当前状态，决策轨迹另存 append-only 表；未纳入必须能回答「为什么」，并给出证据与时间，便于审计。

需求来源：用户 2026-10-28 的两条原始问题，以及随后确认的四项决策——信源「数据库可配置 + 后台管理」、采集库「全量留痕」、「只读审计 + 跳转改判」、扩展优先级四项全选。

## 3. 问题诊断

| 现象 | 原因 |
| --- | --- |
| 加一个源必须发版 | `SOURCES` 是模块常量，`ALLOWED_HOSTS` 是同一文件里的 `frozenset`；配置与代码绑死 |
| 新增 host 的源一抓就死 | `_fetch_items` 的 `host_allowed(result.url)` 只认那 15 个域名，重定向到新 host 直接 `bad_redirect` |
| 采集库不存在 | `raw_items` 只有 `source_name/external_id/title/url/payload` 等字段，无 status/stage/reason；也没有任何读取接口 |
| 被丢弃的条目彻底消失 | `normalize.py` 的 5 个 builder 用裸 `continue` 丢弃；`cluster.py` 的 `should_keep` 同样静默 `continue`，返回值里没有丢弃清单 |
| 截断无记录 | `MAX_RAW_ITEMS=180` 与 `MAX_NEW_EVENTS=50`、`MAX_PANEL_ITEMS=24` 的溢出只是数字减少，没有任何行说明谁被砍了 |
| 裁决历史无法回溯 | `review_decisions` 键是聚类 fingerprint 且 `on_conflict_do_update` 覆盖，只保留「现在的结论」，「怎么变的」被抹掉 |
| 监管类来源进不了档 | `is_notable_official` 对 `category=policy` 返回 False，`should_keep` 把它们当新闻丢掉；`FAMILY_LABELS` 也没有 `policy` 族 |
| 解析器按 key 前缀分派 | DB 源的 key 若撞上 `hf-`/`hn-` 前缀会被送进错误解析器 |
| 后台只能看健康态 | `/sources` 只有成功/失败计数，没有配置面，无法新增或编辑 |

## 4. 方案与实施

### 4.1 核心取舍

1. **单一注册表**：`ingest_sources` 一张表既是配置也是清单，同时是重定向 host 白名单的来源。`SOURCES` 冻结为「种子目录」`SEED_SOURCES`（parity 测试依赖它的顺序与前 17 项），新增候选写在 `catalog.EXTRA_SOURCES`，二者合成 `CATALOG_SEED`；首次运行 insert-or-ignore 灌入，之后代码不再覆盖运维改动。
2. **表空即回退**：`ingest_sources` 为空（含测试环境 `create_all` 之后）时 `registry.enabled_sources()` 回退到 `SEED_SOURCES`，既有用例不需要造数据。
3. **复用 `raw_items` 而不是新建 `collected_items`**：表名被 schema 测试、`functions/lib/db.mjs`、`dev/fake-supabase.mjs` 引用，改名收益为零。用「新增列 + 当前状态」表达现状，用新表 `collect_verdicts` 表达轨迹。
4. **解析派发改为 kind**：`kind ∈ {feed, sitemap, arxiv, openrouter, hf, hn}`，缺 `kind` 时回退旧的 key 前缀规则（保护旧夹具）。
5. **账本 best-effort**：任何账本异常只写 `notes.append("ledger_failed")`，绝不改变收录结果。
6. **不引入物化汇总表**：漏斗来自 `sync_runs.detail.funnel`（单次运行）+ `collect_verdicts` 的窗口聚合，符合 `repo_ops` 明示的「nothing is materialised」。

被否决的做法（与理由）：只在 `sources.py` 加源（改源仍要发版）；独立 `custom_sources` 表只放 RSS（两套注册表、两套健康视图）；`raw_items` 改成每次抓取一行（同一标题反复刷屏，90% 重复）；新建 `collected_items` 并迁移（表名被冻结的 0001 契约与 JS 镜像引用）；给漏斗建汇总表（与「不物化」原则冲突）；从条目 URL 动态扩展 host 白名单（一条被污染的 feed 就能把采集器指向任意地址）；加 arXiv RSS（与现有 arXiv API 源 URL 形态不同，`merge_sources` 去重失效，只会制造重复）；采集库内直接改判（决策入口继续集中在 `#/content`，避免 `audit_log` 动作类型扩散）；本期做 `html_list` 解析器覆盖网信办/工信部（需要选择器配置与页面维护，先把 `kind` 做成列，留成纯增量）。

### 4.3 三个只有写测试才暴露的实现缺陷

这三处不是计划里的条目，是实现过程中被新测试抓出来的，逐条记在这里以免重复踩：

1. **`validate_key` 用法反了**。它抛 `ValueError` 并返回归一化后的 key，`admin_sources.create_source` 却写成 `problem = validate_key(key); if problem:` —— 返回值恒真，新建源永远 400。改为 `try/except ValueError`。
2. **裁决写不回去**。`cluster.merge_sources` 把 evidence 的 `sourceName` 改名成 `name` 并 `pop` 掉原键，而 `Ledger.set_verdict` 用 `evidence.get("sourceName")` 重算 fingerprint，与入账时的 fingerprint 对不上，于是每次运行结束都是 `admitted:0 excluded:0 held:0 pending:289`。修法：`ledger.evidence_identity()` 统一按 `sourceName or name` + `externalId or url` 解析，写入与回写共用；`source_family` 同样取 `sourceFamily or family`。
3. **`seen_count` 一次运行加两次**。两段 flush 都对同一行 upsert，各自 `+1`。改为 `upsert_collected(..., bump_seen: bool = True)`，第二段传 `False`——一次运行就是一次 sighting。

### 4.4 漏斗口径

`sync_runs.detail.funnel` 写 `fetched/parsed/normalized/dropped{code:count}/droppedTotal/capped/clustered/clusterDropped/reviewed/admitted/excluded/held/overEventCap/pending`，恒等式 `parsed = admitted + excluded + held + droppedTotal + pending`，采集库页顶部与「运行详情」共用同一份数据。

### 4.5 上线后才暴露的回填缺口

0004 给 `raw_items` 加了 `status`，列默认值是 `pending`。于是升级前就在库里的行全部读作「等着裁决」，但实际上它们已经被账本上线前的流程处理完，永远不会再动。生产上是 364 行：采集库页面一打开就是一屏无理由的「待定」，而那个页面的全部承诺就是「每一条都能解释自己」。

修法是 0005 数据迁移，把它们标成 `dropped` + `reason_code=legacy_pre_ledger`（`reasons.py` 里标签为「账本上线前采集」）。为什么不用新的 status 值：状态词表与 `GET /library?status=` 是前后端契约，为一个历史批次加第六个值不划算；`dropped` + 一条写清时代的理由在现有词表内表达了同一件事，顺带让 `library-prune` 按常规保留期把它们退掉。

这条缺口不是测试能抓的类：`test_sqlite_schema` 只验证表和列存在，空库上跑迁移也永远不会产生历史行。它只在「有历史数据的库被升级」时显现，所以必须靠上线后的真库巡检发现。

## 7. 发布与回滚

**静态站（Vercel）**：`npm run build` 后随 push 自动部署，本次无静态产物变化。

**API 服务器**：

1. 备份 SQLite（`python deploy/backup.py`，用 `sqlite3.backup()`，禁止直接复制库文件）。
2. 拉代码，`pip install -e backend`（版本号变更会写进 editable 元数据）。
3. `python -m alembic upgrade head` 应用 `0004`。
4. 追加环境变量 `COLLECT_RAW_CAP`、`COLLECT_RETENTION_DAYS`（不配则用默认值 320 / 180）。
5. `python -m app.cli catalog-seed` 把 39 条种子目录写进 `ingest_sources`（`run_sync` 也会自动补齐）。

## 11. 总结

这一版把「信源」和「采到什么」从代码里的常量变成了两套可运维的数据：信源变成一张能改、能探活、能停用的表，采集结果变成一张能按状态、环节、理由筛选的账本，并且第一次让「没纳入的条目」也能回答为什么——规则硬性排除、规则分不足、面板否决或暂缓、批次上限顺延，全部有代码、有中文、有时间、有票型。代价是三条数据（`raw_items`、`collect_verdicts`、`sync_runs.detail.funnel`）每天都在长，所以保留期清理只清 `dropped`、`admitted/excluded/held` 永不自动删；同时因为新增了 `policy` 族，`RUBRIC_VERSION` 升到 `chronicle-v3`，旧票型集体失效重审，这是本轮唯一会改变既有裁决结果的改动，已按可独立回滚的方式落地。
