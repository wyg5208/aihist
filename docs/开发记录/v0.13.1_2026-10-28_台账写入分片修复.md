## 2. 现象

v0.13.0 部署后连跑三轮回补，`notes` 里出现两处 `ledger_failed`：

```
backfill succeeded: raw=1511 created=0 merged=2 admitted=0 held=1
notes: catalog:seeded; catalog:28; archive:2016; ledger_failed; panel:5/5;
       panel_failed:3=invalid_json; review_excluded:149; review_held:1;
       cap:events; ledger_failed
```

后两轮同样是 `ledger_failed`。前三轮 `raw` 是 1511 / 1510 / 1510，而 v0.12.0 那三轮是 1379 / 1379 / 1380——**新增的两个档案源把单轮原始条目数抬了约 130 条**。

`ledger_failed` 是 `pipeline` 对 `upsert_collected()` 与 `insert_verdicts()` 的兜底分支：

```python
try:
    await repo_events.upsert_collected(session, ledger.pending_rows())
    notes.append(f"ledger:pending:{raw_count}")
except Exception:  # bookkeeping never changes a verdict
    notes.append("ledger_failed")
```

也就是说这一轮**没有任何采集台账落库**（`raw_items` 与 `collect_verdicts` 都没写），但运行仍标记 succeeded。审计证据丢了，运行日志看起来却正常。

## 3. 根因

`upsert_collected()` 把整批行塞进一条多行 `INSERT`：

```python
statement = sqlite_insert(RawItem).values(payload)   # payload = 全部 1,511 行
```

SQLite 给每条语句的参数上限是 `SQLITE_MAX_VARIABLE_NUMBER`（3.32 之后为 32,766），而 `raw_items` 有 23 列：

| 单轮行数 | 绑定参数 | 结果 |
| --- | --- | --- |
| 1,379（v0.12.0） | 31,717 | 通过 |
| 1,510（v0.13.0） | 34,730 | `too many SQL variables` |

两种行数都在本机 SQLite 3.50.4 上实测过，边界就在这中间。也就是说：**这不是档案源的错，是写入路径一直贴着上限跑，新源只是把它推了过去**。`insert_verdicts` 之后同样失败，因为它也在同一批行数上工作。

## 4. 修复

`repo_events.py` 增加统一的分片：

```python
WRITE_BATCH_ROWS = 500

def _batches(rows):
    return [list(rows[start:start + WRITE_BATCH_ROWS])
            for start in range(0, len(rows), WRITE_BATCH_ROWS)]

async def _insert_ignore_batched(session, model, rows) -> int:
    inserted = 0
    for batch in _batches(rows):
        result = await session.execute(_insert_ignore(session, model, batch))
        inserted += max(result.rowcount or 0, 0)
    return inserted
```

改到分片上的写入点：`insert_events`、`upsert_seed_events`（插入与刷新两半）、`insert_raw_items`、`upsert_collected`、`insert_verdicts`。500 行 × 23 列 = 11,500 参数，两种方言都在安全区，一次 1,500 行的回补只需三条语句。

`upsert_collected` 的 `on_conflict_do_update` 参数（含 `seen_count = seen_count + 1`）改由内层 `statement_for(batch)` 生成，语义不变：仍是一次 commit，仍是「同一指纹第二次见到就更新状态、`first_seen_at` 保留」。

## 5. 为什么上一轮没被发现

1. **兜底把失败降级成一行 note。** `ledger_failed` 不是错误码，`status` 仍是 `succeeded`，除非有人逐条读 `notes` 否则不会注意到。
2. **没有测试覆盖「回补规模」的写入。** 既有测试都是三五行，永远碰不到参数上限；而真实回补一直是 1,400 行这个量级——离上限只差 3%。
3. **v0.12.0 的回补日志是正常的**，所以「台账写入」被默认为已经工作；直到新源把行数推过阈值才暴露。

## 6. 回归测试

`tests/test_archive_sources.py` 新增 `test_a_backfill_sized_batch_reaches_the_ledger`：写 1,510 行 `raw_items`（恰好是生产那一轮的行数）与同数量的 `collect_verdicts`，断言最后一行能读回。没有分片时这条测试会抛 `too many SQL variables`；有分片时它覆盖 4 个批次。

## 8. 发布与回滚

纯代码回滚 + 重启即可，无迁移、无数据修复：`raw_items` 与 `collect_verdicts` 缺的是**审计台账**，不影响 `events` 与时间轴。若要补回这几轮的台账，需要重跑回补（`raw_items` 以指纹 upsert，重跑不会产生重复行）。

## 9. 下一步

1. 复跑一轮回补，确认 `notes` 变成 `ledger:pending:1511` 与 `ledger:verdicts:N`，不再出现 `ledger_failed`。
2. 兜底式 `except` 应该至少带一次 `logger.warning`：这次是「静默丢台账」，下次可能是别的东西。分级思路是「记录不决定裁定」不等于「不记录它坏了」。
3. 写入规模的边界值得写进注释：任何把「一轮最多多少条」调高的改动（`BACKFILL_RAW_CAP`、档案源的 `max_results`）都应同时确认 `WRITE_BATCH_ROWS` 覆盖得住。
