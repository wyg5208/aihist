| 日期 | 2026-10-26 |

上一版 `v0.6.1_2026-10-26_发布收尾与门禁硬化.md` 第九节第 3 条留了一个二选一：**改文档，或改 `register-tasks.ps1` 的周期**。本轮按用户裁定取前者——**计划任务每日 01:05 是事实**，一切以它为准，代码与文案对不上就改代码与文案。

## 二、任务目标

1. 让 `stale` 这个字段说真话：健康站点不再每天有 18 小时自报陈旧。
2. 让仓库里所有"每 6 小时"的说法与生产实际一致。
3. 让计划任务脚本的默认值与生产实际一致，避免下次重装又装回六小时制。
4. 不改采集能力本身：跑一轮的时长、预算、租约、限流一律不动。

## 三、问题诊断

生产机上 `Get-ScheduledTask aihist-sync` 的实测：

| 字段 | 值 |
| --- | --- |
| `StartBoundary` | `2026-10-26T01:05:00+08:00` |
| `Repetition` | 24 小时一次（`NextRunTime = 2026/10/27 01:05:05`） |
| `LastTaskResult` | `0`（成功） |

而代码里写着：

| 位置 | 原值 | 后果 |
| --- | --- | --- |
| `backend/app/api/public.py` | `FRESH_HOURS = 6` | `/api/v1/status` 的 `stale` 每天有 18 小时为 `true` |
| `backend/app/db/repo_ops.py` | `STALE_HOURS = 8`，注释写"cron runs hourly" | 管理台顶部常驻"上次成功采集已是 N 小时前" |
| `backend/app/api/admin.py` | `FRESH_HOURS = 6` | `?trigger=auto` 的去重窗口 |
| `functions/handler.mjs` | `FRESH_HOURS = 6` | 同上两份逻辑的 JS 版 |
| `README.md` / `src/App.tsx` | "每 6 小时" | 对外文案与事实不符 |
| `deploy/windows/register-tasks.ps1` | 默认 `-SyncHours 6` | 重装会装回六小时制，与生产不符 |
| `deploy/cron.d/aihist` | `0 */6 * * *` | Linux 侧同样 |

**一个必须点明的耦合**：`admin.py` 的 `_is_fresh` 与 `public.py` 的 `_is_fresh` 同名、同值，但语义不同——前者回答"要不要真的跑一轮"（去重），后者回答"调度器是不是坏了"（告警）。如果只是把这两个 6 一起改成 26，那么每日 01:05 的那一轮距上次成功只有 24 小时，落在 26 小时窗口内，`?trigger=auto` 会返回 `not_due`——**采集永久停摆**。所以本轮不是改数，是拆东西。

## 四、方案与实施

三个取舍：

1. **拆成两个窗口，而不是调一个数**。`stale` 用节奏窗口（26h），`auto` 去重用短窗口（2h）。一个数无法同时回答"刚刚跑过吗"和"调度器死了吗"，把这两件事绑在一起，长期必然在某个节奏下自锁。
2. **窗口按节奏取值，而不是按感觉**。26 = 每日间隔 24 + 2 小时宽限：晚到的一轮不报警，整整漏掉一天才报。宽限不能给到 24 以下，否则每日任务会在自己的窗口里判自己"还在期内"；也不能给太大，否则停机一天无人知。
3. **脚本改成锚定时钟**，把 `-SyncHours 6` 换成 `-SyncAt 01:05` + `-Daily`。原来的写法是"从现在起 N 小时重复一次"，装的时间不同就会落到不同的钟点；锚定 01:05 之后，重装一次也不会漂。

被否决的方案：

- **只改文档，代码不动**：`stale` 会继续每天红 18 小时，等于把 bug 写进文档。
- **把 `register-tasks.ps1` 改回 6 小时**：生产早已是每日一次，改脚本等于让下一次重装把节奏改掉，且与用户裁定相反。
- **给 `stale` 加配置项**：多一个环境变量就多一处可漂移的真源，当前只有一个部署形态，常量足够。

变更点：

| 文件 | 改法 |
| --- | --- |
| `backend/app/api/public.py` | `FRESH_HOURS = 6` → `STALE_AFTER_HOURS = 26`；`_is_fresh()` → `_is_stale()`（语义从"新鲜"翻成"陈旧"，返回值与 `stale` 字段直接对齐） |
| `backend/app/api/admin.py` | `FRESH_HOURS = 6` → `DUE_HOURS = 2`；`_is_fresh()` → `_recently_succeeded()`；调用点同步 |
| `backend/app/db/repo_ops.py` | `STALE_HOURS = 8` → `26`，注释里的"cron runs hourly"改成每日并加上"与 public.py 同步"的约束 |
| `functions/handler.mjs` | `FRESH_HOURS = 6` → `STALE_AFTER_HOURS = 26` + `DUE_HOURS = 2`；`isFresh()` 拆成 `isStale()` 与 `ranRecently()` |
| `backend/tests/test_admin_metrics.py` | 陈旧用例 9h → 30h；**新增**"20 小时前成功不算告警"用例，把新语义钉住 |
| `deploy/windows/register-tasks.ps1` | 头注释、`-SyncHours`→`-SyncAt "01:05"`、触发器改 `-Daily -At`；analytics 注释随之改 |
| `deploy/cron.d/aihist` | `0 */6 * * *` → `5 1 * * *`，并写明"改这行就要改 `STALE_AFTER_HOURS`" |
| `README.md` | 版本行 `v0.6.3`；第 7 行与第 286 行的"6 小时"改"每天 01:05" |
| `src/App.tsx` | 关于区文案"每 6 小时运行一次"改"每天 01:05 运行一次" |

## 十一、总结

这次改动的实质不是"6 改成 26"，而是发现**一个常量被两个问题共用**：`stale` 问"调度器是不是死了"，`auto` 问"是不是刚刚跑过"。共用时按 6 小时节奏恰好都没暴露，一旦节奏变成每日，两个方向同时出错——放宽则日更任务自锁，收紧则健康站点天天告警。拆分之后，两个数字各自有了明确的约束：26 必须大于等于节奏 + 宽限，2 必须远小于节奏，写进注释，再被一条测试钉住。
