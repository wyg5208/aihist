## 二、任务目标

1. **回答选型问题**：用户问「如何将项目发布到 Vercel 或 Cloudflare」，需要先判断这个仓库有哪些部分搬得动、哪些搬不动，再给可执行路径。
2. **落地 Vercel 通道**：把 `deploy/nginx/aihist.net.conf` 里六条隐式路由行为复刻到平台侧，使 `dist/` 原样部署后行为与自托管一致。
3. **后端不搬家**：SQLite、定时任务、租约、进程内限流四项约束决定了 FastAPI 必须留在原机；用 `api.aihist.net` 只暴露 `/api` 与 `/go` 两个前缀，由 Vercel 做服务端回源，浏览器始终只看 `aihist.net`。
4. **对齐 Windows 安装流程**：`install.ps1` 增加域名参数、默认不再在本机构建前端、校验 `SITE_ORIGIN`；新增 `switch-caddy.ps1` 完成「全站 Caddy → 只回源 Caddy」的可回滚切换。

## 三、问题诊断

### 1. 两个平台都只接得住前半截

| 现象 | 原因 |
|---|---|
| Vercel 与 Cloudflare 都能直接吃 `dist/`，但 `/api/v1/*` 无处安放 | 两家都是静态托管 + serverless 函数，没有持久磁盘；本项目四类状态全部依赖「一台长期运行的机器 + 本地文件」 |
| SQLite 放上去会立刻坏 | WAL 需要本机固定磁盘的文件锁语义，serverless 的文件系统只读或临时；README 边界第一条已写死 |
| 采集搬不过去 | 每 6 小时的定时任务是**长任务**（`RUN_BUDGET_SECONDS=300`），Vercel 的 `crons` 只能触发函数，不能托管一个跑五分钟的进程 |
| 写入口互斥失效 | `sync_state.lease_token`（150 秒 TTL）依赖同一进程同一库的原子写，多实例会被拆散 |
| 限流失效 | `/api/v1/track` 用的是进程内滑动窗口（`_hits` 字典），多实例各算各的 |

结论：能上 CDN 的只有 `dist/`；后端必须留在原机，或者整体迁到 Docker 托管（本轮不做）。

### 2. nginx 有六条行为，平台不会自动继承

| 行为 | nginx 里怎么写的 | 平台缺了会怎样 |
|---|---|---|
| `/admin` → `/admin/` → `admin.html` | `location = /admin` 301 + `try_files` | 运营台直接 404 |
| `/e/<slug>` → `/e/<slug>.html` | `try_files $uri $uri.html` | 无扩展名引用链 404 |
| 未知路径必须 404 | 注释里特意写明「no SPA fallback」 | 错的 URL 返回 200 + 时间轴，SEO 事故 |
| 缓存分层 | `assets` 1 年 immutable、`/e/` 7 天、`sitemap` 1 小时 | 每次刷新拉 158 个页面 |
| 安全头 + `/admin` noindex | `add_header X-Robots-Tag` | 运营台被搜索引擎收录 |
| `/api`、`/go` 反代 | `proxy_pass 127.0.0.1:8000` | 接口与跳转全部 404 |

### 3. 平台的默认行为与产物的规范地址互相打架

| 现象 | 原因 |
|---|---|
| 开 Vercel 的 `cleanUrls` 会让 159 条 URL 全部 308 | `scripts/lib/page-kit.mjs` 的 `pagePath()` 固定返回 `/e/${slug}.html`，canonical、`og:url`、sitemap、JSON-LD 全部指向带扩展名的地址；`cleanUrls` 的语义正是「去掉扩展名并把带扩展名的请求 308 过去」 |
| 不开 `cleanUrls`，`/e/<slug>` 又访问不到 | Vercel 不做 `try_files $uri.html` 的自动补全，静态文件不存在就是 404 |
| 无扩展名访问是真实流量 | README 把 `/e/<slug>.html` 定为引用页规范地址，但站内引用与外部手写链接两种形式都会出现，nginx 一直是两种都收 |

### 4. Vercel 会缓存 external rewrite 的响应

| 现象 | 原因 |
|---|---|
| 管理台可能读到旧数据，POST 完看不到变化 | Vercel 自 2026-04-06 起，新建项目默认按上游 `cache-control` 缓存 external rewrite 的响应；后端的读接口若返回可缓存头，CDN 会替它缓存 |
| 前端 `cache: "no-store"` 挡不住 | 那是浏览器侧的请求指令，管不了边缘节点 |

### 5. Cloudflare 的两条硬限制

| 现象 | 原因 |
|---|---|
| `_redirects` 无法把 `/api/*` 代理到外部后端 | 官方文档明确：200 proxying「只支持站内相对路径，不能代理外部域名」 |
| 走 Git 集成构建会失败或意外暴露路由 | Cloudflare Pages Functions 固定读项目根目录的 `functions/`，而本仓库的 `functions/index.ts` 是 Supabase Edge 参考实现（`Deno.serve` 形式），会被当成 Pages Function 编译；`functions/handler.mjs`、`functions/lib/*.mjs` 也会被当成路由 |

### 6. `install.ps1` 装完会与新形态互相干扰

| 现象 | 原因 |
|---|---|
| 装一次要白跑一遍 `npm ci` + `npm run build` | 脚本把「本机也托管静态站」当成默认形态，而前端已经归 Vercel |
| 结尾提示「point Caddy at `Caddyfile`」会把本机继续留在全站形态 | `Caddyfile` 是「一个源站服务页面 + API」，与 Vercel 回源并存时，本机仍会响应页面请求 |
| `SITE_ORIGIN` 写错没人拦 | 脚本只校验 `DATABASE_URL`；而 `SITE_ORIGIN` 参与拼订阅确认链接（`growth.py` 的 `confirm_url`）与站内来源判定（`track.py` 的 `classify_channel`），写成 `api.aihist.net` 会让邮件里的确认链接全部 404，且短期内无人发现 |

### 7. 切换顺序本身是个陷阱

| 现象 | 原因 |
|---|---|
| 先切 Caddy 再切 DNS，前台会立刻 404 | 新配置只留 `/api` 与 `/go`，本机不再响应页面；此时 `aihist.net` 仍指本机，读者看到的是 404 而不是旧站 |

## 四、方案与实施

### 4.1 核心取舍

**前端上 CDN，后端不搬，用同源回源把它们接起来。** 这是唯一不触碰「SQLite 必须在本机」「采集必须定时跑」两条硬约束的方案，也让 `src/api.ts`、管理台 Cookie（host-only、`Secure`、`SameSite=Lax`）、CORS 白名单三处一行都不用改——回源是服务端到服务端，浏览器看到的始终是 `aihist.net` 一个源。

**用子域 `api.aihist.net` 而不是把后端放在路径上。** 路径级拆分需要平台支持任意方法、任意 body 的透传；子域拆分只需要一条 `rewrites`，且 `Caddyfile.api` 可以独立收口（除两个前缀之外硬 404，连 OpenAPI 文档都不暴露）。

**保持 `cleanUrls: false`，用 `rewrites` 补无扩展名访问。** 反过来（开 `cleanUrls`）会把 159 条规范地址全部 308，等于让 canonical 指向一个会跳转的地址；而改产物去掉扩展名会连带改 `pagePath()`、`check-pages.mjs` 的断言、nginx 的 `try_files`、Caddyfile 的 `try_files`，为一条平台默认值改四处不划算。

**Caddy 不新增服务实例，直接换配置内容。** 服务名、可执行文件、日志目录都不变，只替换它读的那个 Caddyfile。这样回滚就是「把备份拷回去 + 重启」，不需要重新注册服务。

**«换 Caddy» 单独成一个脚本，不塞进 `install.ps1`。** 应用安装与对外暴露的改动时机不同：前者可以反复跑，后者一生效就改变线上行为。分开之后，一次失败的渲染不会留下半装的机器。

**被否决的方案**

- *Cloudflare Pages + Pages Functions 代理 `/api`*：`functions/` 目录与仓库现有的 Supabase 参考实现同名冲突，改目录名要动参考实现与 golden 生成链；`_redirects` 又明确不支持跨域代理。省下的工作量抵不过两条硬限制。
- *Vercel 上跑 Python 后端*：SQLite 无持久磁盘、定时任务无载体、租约与限流无进程，等于把后端重写一遍。
- *把 `src/api.ts` 的 `BASE` 改成绝对地址 + 后端加 CORS 白名单*：能绕开回源，但会让浏览器直接暴露 `api.aihist.net`，管理台 Cookie 变成跨站（`SameSite=Lax` 下不安全），且 CORS 白名单要跟着域名变，是纯负债。
- *给 `/e/:slug.html` 也写一条 rewrite*：`/e/foo.html` 会被重写成 `/e/foo.html.html`。rewrite 用 `[a-z0-9-]+` 约束 slug，天然避开带点的路径。
- *让 `install.ps1` 继续默认构建 `dist/`*：前端已经在 Vercel 构建，本机再跑一遍只是重复劳动与磁盘占用；旧形态用 `-BuildSite` 显式打开。
- *在 `switch-caddy.ps1` 里强行阻断「DNS 还没切」的情况*：判断「apex 是否仍指本机」需要公网 IP，NAT 与云主机会误判；改成黄字警告 + 8 秒等待，把决定权留给操作者。

### 4.3 关键实现细节

**`vercel.json` 与 nginx 的逐条对应**

| nginx（`deploy/nginx/aihist.net.conf`） | `vercel.json` |
|---|---|
| `location = /admin { return 301 /admin/; }` | 不做 301，`/admin` 与 `/admin/` 都 rewrite 到 `/admin.html`（理由见下） |
| `location = /admin/ { try_files /admin.html =404; }` | `{ "source": "/admin/", "destination": "/admin.html" }` |
| `location /e/ { try_files $uri $uri.html =404; }` | `{ "source": "/e/:slug([a-z0-9-]+)", "destination": "/e/:slug.html" }` |
| `location / { try_files $uri $uri.html =404; }` | 不配 fallback，Vercel 对不存在的静态路径天然 404 |
| `location /assets/ { expires 1y; }` | `Cache-Control: public, max-age=31536000, immutable` |
| `location /e/ { expires 7d; }` | `Cache-Control: public, max-age=604800` |
| `location = /sitemap.xml { expires 1h; }` | `Cache-Control: public, max-age=3600` |
| `location /api/ { proxy_pass ... }` | `rewrites` → `https://api.aihist.net/api/:path*` |
| `location /go/ { proxy_pass ... }` | `rewrites` → `https://api.aihist.net/go/:path*` |

**`/admin` 为什么不照抄 nginx 的 301。** Vercel 在 `trailingSlash: false` 下会把 `/admin/` 先 308 成 `/admin`；如果再加一条 `/admin` → 301 → `/admin/` 的 redirect，两个规则互相指，浏览器会拿到重定向循环。改成两条都 rewrite 到 `admin.html`，`/admin` 与 `/admin/` 都 200，且 `admin.html` 里的资源是绝对路径 `/assets/...`，不依赖尾斜杠解析。

**rewrite 用 `[a-z0-9-]+` 约束 slug，而不是裸 `:slug`。** 裸参数会把 `/e/foo.html` 匹配成 slug=`foo.html`，再重写成 `/e/foo.html.html`；这条路径是否触发取决于平台把「文件系统检查」放在 rewrite 之前还是之后，而两种顺序在不同版本上并不稳定。加约束之后，带点的路径根本不进 rewrite，两种顺序结果一致。落地前实测了 `dist/e/` 下 158 个文件名，全部匹配 `^[a-z0-9-]+$`，无一条会漏。

**`/api` 必须显式关掉 CDN 缓存，两条 header 一起给。**

```json
{ "key": "CDN-Cache-Control", "value": "no-store" },
{ "key": "x-vercel-enable-rewrite-caching", "value": "0" }
```

前者覆盖上游返回的缓存头，后者关掉平台对这个项目 external rewrite 的默认缓存开关。少一条，管理台的列表页就可能读到上一次的响应——而 `fetch` 的 `cache: "no-store"` 只作用于浏览器，管不到边缘。

**`SITE_ORIGIN` 做成硬校验，不是提示。** `confirm_url()` 拼的是 `{site_origin}/api/v1/subscribe/confirm?token=...`，而 Vercel 会把 `aihist.net/api/...` 回源到本机，所以链接必须用 apex 域。写成 `api.aihist.net` 时，邮件里的确认链接会打到只开两个前缀的回源面上，直接 404。`install.ps1` 在读到 `SITE_ORIGIN` 与 `-SiteOrigin` 不一致时 `throw`，宁可装不上。

**`-BuildSite` 默认关，旧形态保留。** 默认形态是「Vercel 建前端 + 本机只跑 API」；要回到整站自托管，加 `-BuildSite` 并用 `deploy\windows\Caddyfile`。两条路都在，所以这次不算删除通道。

**`switch-caddy.ps1` 的执行顺序刻意写成「先验证、再动生产」。**

```
渲染模板 → caddy validate（失败则删临时文件并退出，生产不动）
        → 定位服务与 Caddyfile（解析 WinSW 命令行里的 --config）
        → 顺序检查（apex 仍解析时黄字警告，等 8 秒）
        → 备份到 backups/Caddyfile.<yyyyMMdd-HHmmss>
        → 替换 → 重启 → curl 探活 → 打印回滚命令
```

Caddy 的配置文件路径没有登记在注册表里，只能从服务命令行解析 `--config`；解析失败时脚本不猜默认路径，而是打印 `(Get-CimInstance Win32_Service -Filter "Name='caddy'").PathName` 让操作者确认后传 `-CaddyfilePath`。猜错路径等于把配置写到别处，服务重启后仍是旧行为，是最难排查的一种「成功」。

**临时文件用 `trap` 收尾。** 渲染出的 staged 文件写在 `%TEMP%`，只在 `-DryRun` 时有意保留；任何 `throw` 都会经 `trap` 删除，实测抛错后残留为 0。

**新增脚本全英文注释。** 仓库现有 `.ps1` 是无 BOM 的 UTF-8，而 Windows PowerShell 5.1 对无 BOM 的 UTF-8 会按 ANSI 解码，中文注释在 5.1 下可能乱码。`switch-caddy.ps1` 与 `install.ps1` 的新增段落一律英文，避免在不同主机上出现乱码提示。

**README 里的条数是错的，顺带修正。** 原文写「148 条种子」「149 条 URL」「148 个种子页」，而 `npm run build` 实际输出 `pages 158 / sitemap 159`（v0.3.2 补录 10 条之后没同步）。本次只改动了本轮新增段落涉及的数字与「发布」章节，其余 `148` 的表述留给下一次文档专项。

## 七、发布与回滚

**静态站（Vercel，新增通道）**

1. 项目 Import，Framework 选 Vite，Build `npm run build`，Output `dist`（`vercel.json` 已声明，通常自动识别）。
2. **Node.js Version 必须选 22.x**：`engines` 是 `>=22.12.0 <23`，而 `scripts/check-node.mjs` 在 `preinstall` 阶段直接 `throw`，选 24 会连依赖都装不上。
3. 不需要设 `SITE_ORIGIN`，默认值即 `https://aihist.net`。
4. 部署后按验收清单逐条探测，先测 `POST /api/v1/track`。

**静态站（Qoder Sites）**：通道保留，`dist/` 不变，可随时作为备份发布。发布回执仍写根目录 `*.qoder.site`。

**API 服务器（Windows）**：顺序不可交换。

```powershell
install.ps1 -ApiHost api.aihist.net      # 应用：venv / 迁移 / 种子（不再建 dist）
install-service.ps1                      # 服务：改过 api.env 必须重跑，WinSW 的 env 是安装时快照
register-tasks.ps1                       # 定时任务
switch-caddy.ps1 -ApiHost api.aihist.net -DryRun   # 先干跑，确认找对了 Caddyfile 与服务
switch-caddy.ps1 -ApiHost api.aihist.net           # 正式切
```

**顺序陷阱**：`switch-caddy.ps1` 一生效，本机不再响应页面请求。`aihist.net` 的 A 记录必须已经指向 Vercel；脚本会解析 apex 记录并黄字警告 + 等 8 秒，但不阻断（公网 IP 在 NAT 下无法可靠判断）。

**改完 `api.env` 必须重跑 `install-service.ps1`。** `ANALYTICS_LOG_PATH` 从 `access.log` 换成 `access.api.log` 之后，若不重装服务，`aihist-analytics` 每小时读的仍是旧文件——任务照样退出 0，页面上的「AI 抓取」会静默归零。`switch-caddy.ps1` 结尾会比对这一项并告警。

**回滚**

- Vercel：在 Deployments 里 Promote 上一个部署，或 `vercel rollback`。
- Caddy：`switch-caddy.ps1` 把旧文件备份在 `backups/Caddyfile.<yyyyMMdd-HHmmss>`，回滚就是 `Copy-Item <备份> <Caddyfile路径> -Force; Restart-Service <服务名> -Force`，脚本结尾会打印这两行。
- 应用：回退到 `v0.3.2` 代码并重跑 `install-service.ps1` 即可；本轮无 schema 变化，数据库不需要回滚。

**备份**：本轮无迁移、无 schema 变化，未做库快照。若正式切 DNS 前要留快照，用 `deploy/backup.py`（SQLite 备份 API）或 `VACUUM INTO`，不要直接复制 `.db`（WAL 下会得到撕裂快照）。

## 十一、总结

v0.3.2 结束时，这个站只有两个发布形态：Qoder Sites 托管 `dist/`，以及一台 Windows/Linux 机器用 Caddy 或 nginx 同时扛页面和 API。想上 Vercel 或 Cloudflare，`dist/` 是现成的，但 `/api` 与 `/go` 无处安放——因为后端的四类状态（SQLite 文件、6 小时定时任务、150 秒租约、进程内限流）在 serverless 上一条都不成立。

这次没有去改后端，而是把「对外的那一层」拆开了：`aihist.net` 交给 Vercel，`api.aihist.net` 只留两个前缀回源到原机，浏览器始终只看到一个源，所以 `src/api.ts`、管理台 Cookie、CORS 全都不用动。`vercel.json` 把 nginx 的六条隐式行为逐条搬到平台侧，其中三处是这次真正花了功夫的地方——不开 `cleanUrls` 而用带 slug 约束的 rewrite（否则 159 条规范地址会被 308 掉，或退化成 `.html.html`）、`/admin` 用两条 rewrite 而不是照抄 301（否则与 `trailingSlash` 打架成重定向循环）、`/api` 显式关掉 Vercel 新默认的边缘缓存（否则管理台读旧数据）。

同样重要的是安装流程不再骗人：`install.ps1` 默认不再假装本机也托管前端，`SITE_ORIGIN` 写错会直接中断而不是生成一批 404 的邮件链接，`switch-caddy.ps1` 先 `validate` 再备份再重启，并把回滚命令打印出来。唯一没做到位的是顺序——它需要人先切 DNS，脚本只能在边缘提醒 8 秒。

还没验证的部分也写在这里：Caddy 与 Vercel 两侧的真实行为都没跑过，验收清单里有四条空着。配置正确不等于通道可用，这四条测通之前，v0.4.0 只算「通道搭好」，不算「已切换」。
