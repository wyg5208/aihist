## 2. 问题：note 不是诊断

`pipeline` 对两处台账写入的兜底是这样的：

```python
except Exception:  # bookkeeping never changes a verdict
    notes.append("ledger_failed")
```

「台账不决定裁定」这个立场是对的，但它顺带把**失败原因也一起扔了**：v0.13.0 那三轮回补，`notes` 只留下一个 `ledger_failed`，运行仍是 `succeeded`。要不是当时对着行数手算绑定参数，`too many SQL variables` 这层信息根本无从得知——日志里什么都没有，异常对象也没进 traceback。

写下这条待办时的原话是：「兜底式 `except` 应该至少带一次 `logger.warning`：这次是『静默丢台账』，下次可能是别的东西。」

## 3. 改动

`pipeline.py` 落了模块级 logger 与一个帮手：

```python
logger = logging.getLogger("aihist.pipeline")


def _warn_ledger(*, flush, stage, run_id, rows, error) -> None:
    logger.warning(
        "ledger %s flush failed at %s (run=%s, rows=%d): %s: %s",
        flush, stage, run_id, rows, type(error).__name__, error,
        exc_info=True,
    )
```

两处 `except` 改为 `except Exception as error:` 并调用它：

| 写入点 | `flush` | `stage` | `rows` |
| --- | --- | --- | --- |
| 第一次落库（`upsert_collected`） | `intake` | `pending` | `raw_count` |
| 第二次落库（`upsert_collected` + `insert_verdicts`） | `final` | `pending` / `verdicts` | 对应那一步的行数 |

`flush` 不是装饰：**两次写入处理的是同一批行、行数相同**，只靠 `stage` 无法区分是「一条都没写进去」还是「行写进去了、只有轨迹没写」。`stage` 在第二次落库中是个游标——写入 `ledger.pending` 前是 `pending`，走到 `insert_verdicts` 前才改成 `verdicts`，所以异常发生时的标签就是真实失败点。

`exc_info=True` 让文件日志带上完整 traceback；`notes` 里的 `ledger_failed` 保持原样，`status` 也保持原样——**这条改动的边界是只加信号，不改运行语义**。

## 4. 回归测试

`tests/test_archive_sources.py` 加两条，都用 `caplog` 断言日志本身：

- `test_a_failed_ledger_write_warns_and_still_reports_success`：把 `repo_events.upsert_collected` 换成会抛 `RuntimeError("too many SQL variables")` 的桩，跑一轮完整 `run_sync`。断言两次落库各一条 warning（`intake`/`final`），消息里带 `run=<runId>`、`rows=<rawCount>`、`RuntimeError: too many SQL variables`；同时 `status` 仍是 `succeeded`／`partial`，`notes` 里仍有 `ledger_failed`。
- `test_the_warning_names_the_write_that_failed`：只废掉 `insert_verdicts`，复现「行写进去了、轨迹没写」。断言只有一条 warning 且标签是 `final` + `verdicts`，`notes` 里有 `ledger:pending:<n>` 而没有 `ledger:verdicts:<n>`。

第一条覆盖「全丢」，第二条覆盖「半丢」——两种在旧实现里都只剩同一个 `ledger_failed`。
