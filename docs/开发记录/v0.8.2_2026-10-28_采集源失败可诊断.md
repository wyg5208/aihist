## 二、任务目标

来源是 2026-10-28 凌晨对「2026-10-27 自动同步 17 个源里 8 个报超时」的排查（结论：源站没封、代码逻辑没坏，是 60 秒内的瞬时失败 + 错误码把证据抹平了）。落地排查报告里按性价比排序的四项：

1. 修错误分类：`TimeoutException→timeout`、`ConnectError→network`、`RemoteProtocolError→protocol`、其余 `→network`。
2. note 带耗时：`failed:arxiv=timeout(7002ms)`，一眼区分「卡死」与「快速失败」。
3. 失败源同轮重试一次（≤5s，仍在 120s 预算内）。
4. 每源超时 7s → 12s。

另有一条本轮顺带修掉的同类问题：`http_404` 被降级成 `network`（见三·现象 3）。

## 三、问题诊断

### 现象 1：8 个源同一轮全部超时

`D:\srv\aihist\logs\sync.log`：

```
2026-10-27T17:05:02Z start trigger=auto
2026-10-27T17:06:08Z   sync partial: raw=178 created=1 merged=4 admitted=1 held=0
2026-10-27T17:06:08Z   notes: sources:8/17; failed:arxiv=timeout,infoq=timeout,
                       leiphone=timeout,google=timeout,verge=timeout,mittr=timeout,
                       hf-blog=timeout,hf-trending=timeout; panel:5/5
```

次日用生产完全相同参数（`load_sources`、并发 5、每源 7s、预算 120s）连跑 3 轮：`17/17`、`17/17`、`17/17`，所有源最慢 2.5s。

**原因**：不是封禁、不是不可达、不是解析错误（失败源是 `items=0` 而非 `parse_error`），是那 60 秒内的瞬时失败。而 7s 这把尺子本身也偏紧——本轮实测 `leiphone` 最慢一次 **4298ms**，平时 2.0s，抖一下就到上限的六成。

### 现象 2：记录上分不出「真卡死」和「600ms 就失败」

`httpx_fetch` 原来是：

```python
except httpx.HTTPError as error:  # reported as a fixed code, never raised
    raise TimeoutError("timeout") from error
```

**任何** HTTP 层异常都被转成 `timeout`。受控实验（用同一 `httpx_fetch`）证明两种截然不同的故障写进了同一个词：

| 场景 | 真实发生 | 旧记录 |
|---|---|---|
| 不存在的域名（NXDOMAIN） | 613ms 就失败，压根没超时 | `timeout` |
| 黑洞 IP（10.255.255.1 丢包） | 真的卡到 7.0s | `timeout` |

这正是 10-27 那天查不出原因的直接原因：不是数据不够，是**数据被分类器销毁了**。面板侧在 v0.3.1 已经修过同一类问题（`httpx.ReadTimeout` 的 `str()` 是空串，按文本判超时必然误判），采集侧一直没修。

### 现象 3：`http_404` 也被记成 `network`

`_classify_error` 用 `re.fullmatch(r"[a-z_]+", message)` 判断「这个 message 是不是一个码」。`http_404` 含数字，不匹配，于是落到 `"timeout" if timed_out else "network"` 的兜底分支，被记成 `network`。**任何** `http_4xx/5xx` 都这样降级。

### 现象 4：一次抖动丢掉一整个源

`load_source` 单次尝试，失败即返回。对「解析器抽了一下」这种瞬时故障，代价是整轮少一个源。

## 四、方案与实施

### 4.1 核心取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 参考实现怎么办 | **只改 Python，`functions/lib/sources.mjs` 不动** | `/api/*` 由 `vercel.json` 反代到自建 API，JS 侧只剩 `export-golden.mjs` 与 `dev/fixture-fetch.mjs` 两个夹具生成者。解析逻辑仍是逐字节 parity，差异只落在失败侧，已在模块 docstring 里写明三处分歧 |
| 是否重导 golden | **不重导** | `golden/sources.json` 只记 `key/ok/error/itemCount/items`，**不含 `timeout` 字段**；解析路径未改，本轮 `pytest` parity 用例全绿即为证 |
| 12s 还是更长 | **12s** | 17 源 / 并发 5 = 4 波，最坏 `4 × (12 + 5) = 68s`，仍在 120s 抓取预算内，且给后面 5 席评审留出空间。再长会开始挤压评审阶段（10-27 那轮 66s 里抓取最多只占 11s，40 多秒都在评审） |
| 重试几次 | **一次** | 抖动是秒级的，第二次重试的边际收益接近零；一次重试已能把「解析器抽一下」救回来 |
| 哪些错误值得重试 | `dns`/`network`/`protocol`/`timeout` | 这四个是「当下的运气」，其余（`http_4xx`、`parse_error`、`empty_source`、`too_large`、`bad_redirect`）是源自身的属性，重试只是把延迟翻倍 |
| note 里带什么 | **耗时**，不带重试次数 | 耗时直接回答「卡死还是快速失败」，这是排障第一问；重试次数只进结果对象的 `attempts` 字段供测试断言，不进日志行（避免日志格式第二次变动） |

### 4.3 关键实现

错误码映射（`sources.py`）。httpx 对**域名解析**失败是**两层包装**，所以沿 `__cause__` 走 4 层找 `socket.gaierror`：

```python
def _fetch_error_code(error: httpx.HTTPError) -> str:
    if any(isinstance(item, socket.gaierror) for item in _cause_chain(error)):
        return "dns"
    if isinstance(error, httpx.TimeoutException):
        return "timeout"
    if isinstance(error, httpx.RemoteProtocolError):
        return "protocol"
    return "network"
```

`dns` 这一档是四项之外的补充：报告的原始建议只到「其余→network」，而「解析失败 vs 握手被重置」恰好是 10-27 查不动的那个洞，实测 `ConnectError → ConnectError → gaierror` 三层链可稳定识别，故单列。

重试循环（`load_source`）：

```python
while True:
    attempts += 1
    try:
        items = await _fetch_items(source, fetch=fetch, budget_ms=budget_ms)
    except asyncio.TimeoutError:
        error = "timeout"
    except SourceFailure as failure:
        error = failure.code
    except Exception as exc:
        error = _classify_error(str(exc), isinstance(exc, TimeoutError) or "timeout" in str(exc).lower())
    else:
        return {..., "ok": True, "attempts": attempts}

    # A blip gets one more try; a 404 or a mangled feed does not.
    remaining = deadline_ms - int(time.time() * 1000)
    if attempts > 1 or error not in TRANSIENT_ERRORS or remaining <= 250:
        break
    budget_ms = min(retry_ms, remaining)
```

日志行（`pipeline.py`）：

```python
def _failure_note(failed: list[dict[str, Any]]) -> str:
    """`failed:arxiv=timeout(12002ms),infoq=network(613ms)`"""
```

### 4.4 被否决的方案

| 否决项 | 理由 |
|---|---|
| 打开 DNS 客户端操作日志来抓抖动 | `Microsoft-Windows-DNS-Client/Operational` 默认关闭，且只能事后查；分类器修好之后每次失败自带答案，成本低得多 |
| 串行抓取 / 降低并发以换稳定 | 实测并发 5 整轮 6.2s，串行会把墙钟拉到 4 倍以上，而失败与并发没有因果关系 |
| 把每源预算提到 30s | 17 源 4 波最坏 140s，直接击穿 120s 抓取预算，会把「少一个源」换成「整轮砍掉尾部源」 |
| 对 `http_5xx` 也重试 | 5xx 是站点自己的问题，重试只是把 12s 变成 24s；且重试集越宽，越容易在真故障时把预算耗尽 |
| 让 note 也带 `attempts` | 日志格式第二次变动，收益低于成本；`attempts` 留在结果对象里给测试断言 |

## 十一、总结

之前的状态是：采集侧一旦失败，只会留下一句 `timeout`——NXDOMAIN、连接被拒、对端掐断、真的卡死，在记录上完全同形，所以 10-27 那 8 个源只能靠一天后重新抓取来「证明没事」。现在每种失败自带名字和耗时（`failed:arxiv=timeout(12002ms)` 与 `failed:infoq=dns(231ms)` 是两件完全不同的事，处置动作也不同），瞬时抖动有第二次机会，单源预算从 7s 抬到 12s 从而不再被正常的握手方差击穿。改动只落在失败路径上，解析结果、契约夹具、种子与接口字段一个字节没动——这是本次一次性把四件事做完仍然只有两个代码文件的原因。
