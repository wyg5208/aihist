**五个国产大模型当评审，三票才准入库：一个 AI 编年史的内容管线**

## 二、正文（可直接复制到掘金）

---

我维护一个 AI 编年史站点，158 条条目，从 1912 年的国际象棋自动机到 2026 年 10 月。每条带 1–2 个可点开的原始来源。

做这件事最大的风险**不是漏，是编**。漏一条没人知道；编一条，整份档案就失去被引用的资格——因为别人引用你的唯一理由，是他相信你没编。

所以这个项目里投入最多的不是内容，是评审机制。这篇讲它是怎么装起来的，以及它在什么情况下**故意不工作**。

## 一、第一道闸：规则预筛，一分钱不花

大模型评审是付费的。在花钱之前，先用确定性规则砍掉明显不该进档案的东西：

```python
HARD_RULES: list[dict[str, Any]] = [
    {
        "key": "funding",
        "label": "融资、估值与资本事件",
        "pattern": compile_ascii(r"融资|募资|估值|亿元|千万美元|亿美元|[A-E]轮|IPO|上市|收购|并购|股价|市值|投资机构"),
    },
    {
        "key": "personnel",
        "label": "人事、裁员与组织变动",
        "pattern": compile_ascii(r"任命|离职|裁员|加盟|出任|晋升|招聘|高管变动|人事变动"),
    },
    ...
]
```

融资、人事、股价这类事件有个共同点：**当时热闹，一年后没人引用**。而编年史的单位是年，不是天。规则命中即硬性排除，不看分数、不进面板、不给翻案机会。

预筛给出 0–100 的分数后，用两个阈值分流：

```python
RULE_PANEL_THRESHOLD = 35
RULE_AUDIT_THRESHOLD = 25
```

- **≥ 35 且未命中硬规则**：值得花一次评审费，送五席面板；
- **25–35**：落库，标记待人工审计，不送面板；
- **< 25**：直接判 `excluded`（有记录，但不展示、不占待办）。

分流的判断就一个函数：

```python
def should_audit_out(assessment: dict[str, Any]) -> bool:
    if assessment.get("disqualify"):
        return True
    return assessment["score"] < RULE_AUDIT_THRESHOLD
```

注意它返回的是“可以给出结论了”，而不是“扔掉”。低分段落的不是黑洞，是 `excluded`——有日志、可回溯，但**不会变成一个等你三天后想起来处理的状态**。

这里有个刻意的设计：**不给低分段留待办**。任何“先存着以后看”的队列，三周后都会变成一个你不再打开的页面；而一个每次运行都能自我结案的管线，才能无人值守地跑下去。

## 二、第二道闸：五席、三票、75 分

真正的常量在这一段，注释比代码重要：

```python
# v2: the panel moved from three judges / two votes to five vendors / three
# votes. The bump is what retires the cached v1 ballots, so decisions taken
# under the old quorum are re-reviewed instead of reused.
RUBRIC_VERSION = "chronicle-v2"
INCLUDE_SCORE = 75
# One judge per domestic vendor: DeepSeek, Qwen, GLM, Kimi, MiniMax. Five
# vendors rather than five copies of one model, so no single vendor's bias can
# carry a decision.
PANEL_SIZE = 5
# A bare majority. Two outages still leave a decisive three-vote quorum, while a
# 2-2 split holds instead of being broken by whichever judge answered first.
MIN_INCLUDE_VOTES = 3
```

三个数字，对应三个不同的问题：

| 常量 | 值 | 挡的是什么 |
|---|---|---|
| `PANEL_SIZE` | 5 | 单一厂商的偏好能不能改写结论 |
| `MIN_INCLUDE_VOTES` | 3 | 两席挂掉还能不能决，平票怎么办 |
| `INCLUDE_SCORE` | 75 | "我觉得重要"和"够格入档"的差距 |

计票函数不长，但它有一个容易被忽略的细节——**默认值是 hold**：

```python
        include_votes = sum(1 for vote in votes if vote["vote"] == "include")
        valid_votes = len(votes)
        exclude_votes = valid_votes - include_votes
        score = median([vote["score"] for vote in votes])
        decision = "hold"
        if valid_votes >= MIN_INCLUDE_VOTES:
            if include_votes >= MIN_INCLUDE_VOTES:
                decision = "include"
            elif exclude_votes >= MIN_INCLUDE_VOTES:
                decision = "exclude"
```

先写 `decision = "hold"`，再在条件成立时覆盖。这样任何"没想到的情况"——有效票不足 3 张、5 票里 2 比 2、字段缺失——都自动落到 hold，不需要在 5 个分支里各写一次兜底。

这就是失败关闭（fail closed）最朴素的写法：**默认值必须是安全值，而不是空值**。

另外注意投票门槛是**双条件**：评审要投 `include` **且**分数 ≥ 75 才算一张同意票。只在提示词里说"分数不低于 75 才投 include"是不够的，模型会自己说服自己；代码里再算一遍，才是硬的。

## 三、为什么是五家厂商，不是五个副本

同一个模型跑五次，得到的不是五票，是一票加四份抄写。它甚至会因为采样温度不同而在错误结论上更加自信。

所以五个席位固定为 **DeepSeek / Qwen / GLM / Kimi / MiniMax**，一家一席。配置校验里有一条很硬的规则：**模型 ID 重复即视为面板不成立**（`configured=false`），不是警告，是拒绝运行。

这条规则的价值在我经历的两件事的对比里体现得最清楚：

**一次升了，一次没升。**

把面板从"三席两票"改成"五席三票"时，门槛的**语义**变了：旧票是按 2 票多数投出来的，和 3 票多数不可比。处理办法是升 `RUBRIC_VERSION` 到 `chronicle-v2`——票型以 rubric 版本为键（`review_decisions` 表上就有一个 `ix_review_decisions_rubric` 索引），版本一变，旧票全部作废，待评审条目重走一遍。

后来补齐第五席密钥时（规则没变，仍是五席三票，只是运行时少了一席），我们决定**不升**：旧的四票决策仍满足"≥ 3 票 include"，重审只会白烧 24 条候选的 token；新产生的五票决策会自然覆盖同一条目。

判据一句话：**变的是"什么算通过"，就升版本；变的是"谁在场"，就不升。**

顺带一个教训：这次补席位的一轮烟测里，`glm-4.7` 报了 `network` 而不是 `timeout`。原因是 `httpx.ReadTimeout` 的 `str()` 是空字符串，而旧代码靠文本匹配判断超时类型——**异常分类靠字符串匹配，迟早会静默错位**。后来改成按异常类型判断（`asyncio.TimeoutError` / 类名里含 `timeout`）。这类 bug 不会报错，只会让日志里的原因栏骗你。

## 四、一次真实的 2-2：503、四席、六条 hold

机制说得再好听，不如看一次真实运行。这是门禁 G4（收录门槛）的输出，脱敏后原样贴：

```
ok   invalid judge output fails closed
ok   split panel is reported as 4/5 with one failure — seed:158; panel:4/5; panel_failed:3=http_503; review_excluded:44; review_held:6; cap:events
```

读一下这行：

- `panel:4/5` —— 五个席位里第 3 席返回 HTTP 503，剩四席；
- `panel:4/5` 之后**没有崩，也没有降级成"少数服从多数"**；
- `review_excluded:44` —— 44 条被判不入档；
- `review_held:6` —— 6 条落 hold，**没有一条因为"凑不够票"被默认放行**。

四席有效票时，2 比 2 是常态。如果实现成"平票时放行"，这 6 条就会全部进档案，而且没有任何日志会告诉你这件事发生了。`decision = "hold"` 这一行的意义，就是这种时候。

把完整流转画出来是这样（`editorial_status` 默认为 `NULL`，后台视图里把这类行叫作 legacy）：

```
未评审（editorial_status = NULL）
   |
   |-- 命中硬规则 或 分数 < 25 -------------> excluded   有记录，不展示
   |-- 25–35，或有效票不足 3、平票、席位失败 --> hold       可复审，不展示
   `-- 有效票 >= 3 且 median(score) >= 75 ----> admitted   展示
```

注意并不存在 "rejected but visible" 这种中间态：`hold` 和 `excluded` 都不上站，区别只在于前者还值得再看一次。

### "席位缺失"其实是两件事

代码里把它们分开了，因为处置完全不同：

**配置层**——解析出的席位少于 3、模型 ID 重复、缺 base 或缺 key，直接 `configured = false`，整批评审不启动：

```python
models = [judge["model"] for judge in judges]
reason: str | None = None
if len(judges) < MIN_INCLUDE_VOTES or not all(models):
    # Fewer judges than the quorum could never admit anything.
    reason = "models"
elif len(set(models)) != len(judges):
    reason = "duplicate_models"
elif not all(judge["base"] for judge in judges):
    reason = "base"
elif not all(judge["key"] for judge in judges):
    reason = "key"

return {
    "configured": reason is None,
    "reason": reason,
    "judges": judges,
    "models": models,
    "timeoutMs": timeout_ms,
}
```

**运行层**——席位都在，但某个模型超时或返回不能解析的 JSON，该席产出一张 `_failure(judge, "timeout" | "network")`，不进票箱：

```python
        for result in results:
            if not result["ok"]:
                continue
```

这三行的 `continue`，就是"坏票不计入分母"的全部实现。少了它，一次 503 会被当成一张 exclude 票——错误不再是"结论模糊"，而是"结论更自信地错"。

## 五、可核验的产物：让"相信我"变成"去核对"

评审机制对外不可见时，它只是一句自我表扬。所以每条链路都留了可核验的出口：

| 产物 | 位置 | 用来干什么 |
|---|---|---|
| 158 条带来源的条目 | `/e/<slug>.html` | 无 JS 静态页，含 canonical、OG、JSON-LD；生产库 158 条全部 `admitted` |
| 194 条来源链接 | 每条 1–2 个 | 论文 DOI、官方博客、机构页面、专利库 |
| 规则全文 | `/api/v1/standard` | 五维评分表 + 硬排除清单，公开 JSON |
| 每个条目的纠错入口 | 页脚「发现错误？」 | mailto 模板已填好条目与链接 |

评分的五个维度是公开的，就写在那张 JSON 里：主体与时点明确 / 与 AI 发展直接相关 / 证据可核验 / 有历史增量 / 一年后仍可引用。

注意最后一条。**"一年后仍可引用"是这份档案真正的收录标准**——它一次性排除了所有"当时很热"的东西，也让"融资/人事"这类硬排除规则显得不冤。

## 六、八步门禁：检查器自己也要被检查

这套管线的全部验收压在一个命令里：

```
$ npm run release:gate

  G0  ok                             0.1s  version consistency
  G1  ok                            11.7s  build (tsc + vite + static pages)
  G2  ok                             0.6s  static pages, sitemap, robots
  G2b ok                            11.6s  static page checker self-test
  G3  ok                             1.5s  ingest pipeline
  G4  ok                             2.3s  editorial gate
  G5  ok                             1.3s  benchmark coverage
  G6  ok                           107.2s  backend tests (pytest)

Release gate passed.
```

总计 136.3 秒，`G6` 的 274 个测试占了大头。八步里最值得单说的不是 pytest，是 **G2b**。

`G2` 检查静态页：页面存在、canonical 正确、JSON-LD 能解析、内部链接指向真实条目。问题是——**检查器自己坏了怎么办？** 一个永远返回 true 的检查器，会让所有人睡得很香。

G2b 就是为这个问题写的：它拿正式产物做 21 个副本，其中 1 个是未篡改的对照组（必须通过），另外 20 个各注入一处真实缺陷——

```
missing page / orphan page / wrong canonical / wrong JSON-LD type / broken JSON-LD
missing evidence link / unescaped ampersand / wrong citation access date / source heading count
unknown internal link / injected external stylesheet / injected inline script
sitemap missing url / sitemap duplicate url / sitemap wrong lastmod / robots without sitemap
homepage description drift / homepage duplicated site JSON-LD / homepage SearchAction
homepage missing asset
```

每个副本都必须在**指定的那一条**上报警，报在别处也算失败。实测输出：

```
Static page self-test: 21/21 cases passed.
```

这套东西第一次真正救我的时候，是加纠错入口那一版。每个条目页页脚加了「发现错误？」，链接形如 `/api/v1/correct?slug=turing-1950`。页面一构建，`G2` 立刻红了 **158 处**——检查器认为这 158 个内部链接指向不存在的地址（它只认识 `/e/<slug>.html`）。

最省事的修法有三种，都不该选：把链接改成绝对 URL（检查器管不到外部域名）、加个 `if href.includes('/api/') return true`（等于给这一类链接开白名单）、或者直接调低检查强度。

最后做的是第四种——**给检查器增加一条它原本不认识的路由，但保留同一套存在性校验**：

```js
// The correction page is a live route rather than an archive address: the
// slug travels as a query parameter, so the same "does this entry exist"
// question applies to it.
if (href.startsWith("/api/v1/correct?slug=")) {
  return slugs.has(href.slice("/api/v1/correct?slug=".length));
}
```

三行。语义是"这条路由此前未知变为已知，但**校验强度不变**"——`slug` 仍必须在 `slugs` 集合里，写错一个 slug 照样红。

这就是 G2b 存在的理由：**红线的作用是保证检查真实存在，不是让构建变绿。** 一个为了让门禁通过而被削弱的检查器，比没有检查器更危险，因为它会持续给你虚假的安全感。

## 七、复盘：三件我改了主意的事

**1. 票数不是越多越好，是"厂商数"越多越好。** 最初想用同一个模型跑 5 个席省事，试了两轮就放弃了：同一模型在同类候选上的失误高度相关，五票的信息量接近一票。现在模型 ID 重复直接拒绝运行。

**2. 平票不能"再问一次"。** 曾经设计过平票时追加一轮复审，很快发现这是给"想要的那个答案"留后门——追加轮次会把不确定性洗成确定性。现在 2-2 一律 hold，宁可少收一条。

**3. 纠错宁可轻，不要重。** 最初想做一个完整的纠错提交表单（落库 + 审核队列）。最后上线的是 mailto 轻量版：页脚一个链接，邮件模板已填好条目和 URL，用户按发送就行。理由是纠错量在早期必然很低，为每周 1 条需求维护一套工单系统不值得。**触发条件写死：每周纠错超过 5 条，再换落库队列。**
